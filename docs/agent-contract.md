# Agent contract

oasis is for any agent. One policy table in the core, `tools/policy.py`, lists every operation, its
tier and the reason; docs, skills, messages and any harness guard follow it. Read it as JSON:

```bash
~/.agents/skills/oasis/oasis policy --json
```

It runs anywhere, also before a workspace file exists. The output holds `version`, `tiers` (what
each tier means), `harness` (what a harness does with each tier for its agent: `allow`, `ask`,
`deny`) and `operations`, one object per row with `operation`, `tier`, `kind` (`oasis` command,
`program` outside oasis, or `action`), `reason`, `example` (a command line of that operation, `null`
for an action) and `confirm` (what `--confirm` takes, `null` when the command takes none).

## Tiers

- **A**: the agent does it alone; reversible or rebuildable.
- **B**: the agent proposes it and a person confirms it explicitly; data loss or hard to undo.
- **C**: only a person does it.

Changing a tier is a contract change: a decision, a note in the README and in the changelog.

## Tier B in the CLI: `--confirm <exact name>`

`drop-database`, `gc --apply --trash`, `migrate --apply`, `worktree-init`,
`recreate-database-volume` and, since v0.20.0, `init-dev-database` (the one command that creates a database)
run only with `--confirm` naming exactly what they change:

| Command | `--confirm` |
| --- | --- |
| `drop-database <name> [--terminate]` | the database name |
| `gc --apply --trash [--older-than <days>]` | the project root (`--project`) |
| `migrate [--workspace <dir>] --apply` | the workspace file the plan writes (`write <dir>/oasis-workspace.toml`) |
| `worktree-init <feature> <branch> [--path <dir>]` | the worktree path the plan names (`worktree: <path>`) |
| `recreate-database-volume` | the compose project (the top-level `name:` of the compose file, `compose_project=<name>` in the plan); see [The database account](setup.md#the-database-account) |
| `init-dev-database [--with-demo] [--lang <code>] [--country <code>] <module> <name>` | the database name |

Without it, or with another value, the command changes nothing, exits 2 and names the exact
command to run, for example:

```text
ERROR: drop-database moves shop_dev_old and its filestore to the trash (Tier B: it needs explicit confirmation); nothing changed. Run: oasis --project /work/shop drop-database shop_dev_old --confirm shop_dev_old
```

`--confirm` records explicit intent: the agent proposes the command, a person agrees, then it runs
with `--confirm`. It is not a guarantee against an agent that adds it by itself; where a harness
exists, its dialog is the confirmation (see [Bash guard](bash-guard.md)). `worktree-init --dry-run`,
`migrate --plan` and resuming an existing worktree need none.

Decision (v0.20.0): a database is created only when the user asks for it, with what Odoo's database
manager form asks, as the user chose it. `init-dev-database` is the one command that creates a database,
through Odoo's own database creation, and it is Tier B; its `--dry-run` prints the database it would create
and changes nothing; `init-dev-database --plan --json` lists the questions the agent relays to the user (the
suffix after the workspace's prefix, dev, test or both, the module, demo data or not, the language and the
country) and, once answered, the dry run and the exact `--confirm` command of each database
([The plan of a new database](dev-database.md#the-plan-of-a-new-database)). `install-module` installs into an
existing database only (Tier A): a missing one exits 2 naming `init-dev-database --plan` before Odoo starts,
which would create it. The command that created an empty PostgreSQL database is gone (README). The
disposable databases of `test-module` and `verify-module`, and their kept test database (`--reuse`,
`[tooling].test_database`), stay Tier A: they are part of testing.

Decision (v0.16.0): `stop --database` stays Tier B. It stops the database service every checkout
shares, which ends the sessions of a running server on that database (the command already refuses
while another checkout's server runs). It takes no `--confirm`: the Gentle Shell dialog confirms it.

## Harnesses

A harness guard takes its tiers from this table. The Gentle Shell layer reads it from
`pi/lib/policy.generated.ts`, generated by `python3 -B tools/policy.py --typescript`; a test fails when
that module drifts from the table, and another runs every `example` through the guard. Tier A runs,
Tier B waits for the user's confirmation in a dialog (`[tooling].agent_destructive` can make it
`deny` or `allow`), Tier C is blocked; see [Bash guard](bash-guard.md).
