# Disposable test databases

Without an explicit database argument and without a configured `test_database`, `test-module` and the tests phase of `verify-module` use a new database for every run:

- Name: `<test_prefix><module>_r<6 hex>` (`<test_prefix><slug>_<module>_r<6 hex>` in a checkout with a slug), random per run. When it would exceed 56 bytes, the module part becomes its first characters plus `_` and the first 4 hex of the module name's SHA-256, so the name is at most 56 bytes and `verify-module`'s `<name>_update` sibling still fits in 63. A test prefix and slug that leave no room exit 2 before anything runs.
- Reserved names: a name ending in `_r` + 6 lowercase hex, optionally followed by `_update`, belongs to these runs. An explicit database argument or a configured `test_database` with such a name is refused with `Database names ending in _r<6 hex> are reserved for disposable runs: <name>` (exit 2, nothing runs) by `test-module`, `verify-module`, `install-module`, `update-module`, `odoo-shell`, `start -d`/`--database` and `init-dev-database`. `drop-database` (which moves them to the [trash](trash.md) like any other database) and `module-status` accept them (cleanup and inspection), and so does `gc`. The phases of a disposable `verify-module` run use its names because that `verify-module` process holds their live run locks.
- Before the database exists, the run creates a lock `runs/<database>.json` (`pid`, `started_at`, `database`, `project_root`, `argv`; 0600) in the checkout's private runtime state directory (see [Servers and ports per checkout](servers-and-ports.md)). The lock is created exclusively (`O_EXCL` on its final path, then written and fsynced): when a lock of that name already exists, live or left by a killed run, the run exits 2 with `Disposable test database is locked: <name>` and touches neither that lock nor the database. A name that already exists as a database is refused (`Disposable test database already exists: <name>; it was left as it is.` and `Run the command again for a new name; oasis gc --apply drops what interrupted runs left.`, exit 2) and never touched. The database is then created; it becomes the run's own once `createdb` succeeded. When `createdb` fails, the run checks the name again: if the database exists now and no live run of the current user (in any checkout) holds another lock of that name, `createdb` created it before failing, so it is the run's own and is dropped like any other (`Cannot create disposable test database <name>; it was created anyway and is dropped.`); otherwise (for example the name was taken by another run in the meantime) the run reports `Cannot create disposable test database <name>; it was not dropped.`, drops nothing and removes only its own lock. Either way the run exits non-zero and no tests run. When `createdb` itself reports that the name already exists, the database was created by someone else and is never dropped; only a database that `createdb` created before failing for another reason is treated as the run's own. Otherwise the tests run exactly as for a shared destination, and at the end the run always closes the database's sessions, drops it, removes its filestore directory `<data_dir>/filestore/<database>` and removes the lock: after success, after failing tests, and after SIGINT (Ctrl+C) or SIGTERM. `<data_dir>` is `[tooling].data_dir` when it is set (see [Path-free odoo.conf](path-free-odoo-conf.md)); otherwise `data_dir` is the only other option read from `odoo.conf` for this, and without an absolute `data_dir` the filestore step is skipped (Odoo's default data directory is not guessed). `gc --apply` removes filestores the same way.
- `tools/test_temp.py` owns this cleanup, because it already owns the signals: `test-module` execs it, so a SIGTERM to the `test-module` process or a Ctrl+C to its process group reaches it; it forwards the signal to Odoo and cleans up when Odoo has ended. `verify-module` takes the locks of both of its databases first (the same exclusive rule; while it takes and records each lock, SIGINT and SIGTERM are deferred and the lock helper runs with them ignored, so a signal then ends the run right after the lock is recorded and no lock is leaked), then checks that both names are free, and from then on drops both from an exit trap (before that, the trap removes only the locks it wrote); Bash runs that trap when the phase in progress returns, so a SIGTERM sent only to `verify-module` takes effect when that phase ends. SIGKILL or a lost machine cannot clean up: `oasis gc` finds what is left.
- With `--compact`, `test-module` runs the tests in a child process: a SIGTERM sent only to the outer process ends it without the summary, while the run still finishes and drops its database; a Ctrl+C reaches both.
- A database that cannot be dropped keeps its lock and is reported on stderr (`Cannot drop disposable test database <name>; run oasis gc --apply later.`); the run then exits non-zero.
- With `--compact`, the `test-module` summary gets one line after `phase=tests database=<name> exit=<n>`: `database_lifecycle=disposable dropped=<yes|no>`. It is the run's own cleanup result, which `tools/test_temp.py` writes to the file `database_lifecycle` of the run's log directory: `yes` means the run left no database behind (dropped, or never created, for example because the name was locked); `no` means the drop failed, or the run ended without reporting (killed). `verify-module --compact` prints the same line as its last line, from its own drops of both databases. Without `--compact` neither command prints it. Shared destinations print no such line.

## Cleaning up after interrupted runs

```bash
~/.agents/skills/oasis/oasis --project /absolute/project gc            # list, change nothing
~/.agents/skills/oasis/oasis --project /absolute/project gc --apply    # drop them
~/.agents/skills/oasis/oasis --project /absolute/project gc --all-checkouts
```

`gc` lists the disposable test databases of this checkout's namespace that no live run holds, one `orphan <name>` line each, then `orphans=<n>`; it changes nothing. A run is live while the pid of its lock (in any checkout of the current user) still runs the command line recorded in the lock, so a reused pid does not keep an orphan alive (Linux `/proc`, like server records). With `--apply` it closes each orphan's sessions, drops it, removes its filestore and its stale lock, printing `dropped <name>`. An orphan whose drop fails prints `failed <name>` on stderr, keeps its filestore and lock, and the next orphan is still dropped. The run ends with `dropped=<n>` and `failed=<m>` and exits 1 when `m` is not 0, otherwise 0 (also when there is nothing to do).

- Namespace: a checkout with a slug owns `<test_prefix><slug>_...`; the main checkout (or a project outside git) owns `<test_prefix>...` except the namespaces of its existing linked worktrees (their slugs come from `git worktree list`: the worktree's `checkout_slug`, else the slug of its folder name). Leftovers of a worktree that no longer exists belong to the main checkout. Slugs still match as prefixes: a checkout skips the namespaces of other existing checkouts that start with its own (`wt` skips `wt_1_`). `list-databases` (and so the menu's database choices) applies the same namespace to every database under both prefixes (see [Fresh development database](dev-database.md#listing-this-checkouts-databases)).
- `--all-checkouts` lists every namespace of the test prefix. A checkout with a slug may drop only its own databases, so `--apply --all-checkouts` runs only in the main checkout (elsewhere it exits 2 before changing anything).
- Only names with the run suffix are candidates: development databases, test databases without it, the configured `test_database` (with its `_update` sibling) and the [trash](trash.md) are never touched (`gc --trash` handles the trash). Databases of another OS user's runs on the same PostgreSQL server have no visible lock; run `gc --apply` only for your own projects.
- A lock left by a run killed before its database existed has no database for `gc` to find, so it stays (its random name is never reused; locks live in the per-user runtime directory, usually cleared at logout or reboot).
- There is no project wrapper and no agent tool for `gc`; the bash guard does not block it.
