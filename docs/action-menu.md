# Action menu

`oasis menu` lists the everyday operations of a checkout so you can run them by hand without remembering the commands. Run it yourself in a terminal:

```bash
~/.agents/skills/odoo19/oasis --project /absolute/checkout menu
```

- When it opens it prints the checkout (`checkout: main`, or the worktree slug), its server (`server: running on port <port> (pid <pid>)`, `server: stopped` or `server: unknown (<reason>)`) and the default database of *Start / restart the server* (`default database: <name>` or `none`).
- Groups and actions, numbered: **Server** (*Start / restart the server*, stop, show the end of the server log, follow the server log, status, stop the database service), **Modules** (install with or without demo data, update, module state, a development database with role accounts through `init-dev-database`, a module's overview from source through `module-info`), **Tests** (a module, one class or method, reusing the test database) and **Databases and maintenance** (create, move a database to the [trash](trash.md), list the trash, restore from it and empty it with `gc --apply --trash`, list and drop leftover test databases with `gc`, `doctor`, the `migrate` plan and `migrate --apply`, `worktree-init`).
- *Start / restart the server* asks, in order: the database (Enter takes the default: the last database this action used in this checkout, else the development database of the checkout's only module (`<dev prefix>[<slug>_]<module>`), else none; `-` chooses none), the dev mode (a closed numbered list built from the series table in `tools/odoo_versions.py`: `off`, `all (access, qweb, reload, xml)` on 19.0, each feature, and `reload,xml`; Enter is `off`), and the HTTP port (Enter keeps the port the command will use: the running server's, else `start`'s rule for this checkout; a typed one must be 1-65535, `Port must be a number from 1 to 65535.`). A dev mode that turns on `reload` when the checkout's environment Python can import none of its packages prints `Warning: reload needs inotify or watchdog importable by <python>; none is, so Odoo will log a warning and disable reload.` (it does not block). The command is `start --detach` when the checkout's server is stopped and `restart` when it runs, with `-d <database>`, `--dev <mode>` and `--http-port <port>` only for what was chosen. Without a database it prints what Odoo will do instead: `No database chosen: Odoo will use odoo.conf's db_name (<name>).`, `No database chosen: odoo.conf sets no db_name, so Odoo starts without a database.`, or, when restarting a server that has one, `No database chosen: restart keeps the database of the running server (<name>).` Then `Run this command? [y/N]: `; anything but `y` or `yes` prints `Not confirmed: nothing ran.` (exit 1). The catalog keeps the older *Start the server in the background* and *Restart the server* for older panels; the menus do not list them.
- Repeat: after an action ran, from this menu or the Gentle Shell panel, its id and answers are kept in `menu.json` (0600) in the checkout's private runtime directory (next to `server.json`; it survives `stop`; it holds module, database, port and dev mode names, never a secret). Actions only the user runs and the terminal-only one are not kept. While the action is still in the catalog and its answers still fit (the module exists, the values match their patterns and choices), the group menu lists `  r) Repeat: <label> (<short answers>)` first and asks `Group (r to repeat, q to quit): `; `r` shows its command and asks the same confirmation as the first time (typed name or `yes`, `y` for start / restart), then runs it. The group numbers do not change.
- Inputs: modules come from the checkout's addon roots, databases from `list-databases` (which starts the database service as it does today; the menu prints `Listing databases (this may start the database service)...` first). A database can also be typed; a number picks from the list and is never taken as a name (`Choose a number from 1 to <n>, or type a name.`). Test classes are checked like `test-module --only`. An invalid answer is asked again; `q` quits.
- Before anything runs it prints `Command: <the exact command>`. Start / restart then asks `y`, as above. Destructive actions ask you to type the database name (`drop-database`) or `yes` (`stop --database`, `gc --apply`, `gc --apply --trash`, `migrate --apply`); any other answer prints `Not confirmed: nothing ran.` (exit 1). One action per run; the exit status is the command's. *Follow the server log* runs `tail -n 200 -f` on `server.log` after `Following <log>; press Ctrl+C to stop.`; Ctrl+C ends it with `Stopped following the server log.` and exit 0.
- It needs a terminal: with stdin not a TTY it exits 2 with `oasis menu needs a terminal (stdin is not a TTY); run it yourself, or print the actions as JSON with --catalog.` So an agent cannot drive it, even in a form the bash guard does not recognize.
- The bash guard of the Gentle Shell layer also blocks agents from running it, as a guard rail on top of that refusal (not a sandbox): `oasis menu` and `odoo19 menu` (by any path to the entry point) in every session, `--catalog` included, and the menu's scripts `tools/menu` and `tools/actions.py`, judged by the file they are rather than by how they are spelled. Each script word is resolved against the session's working directory and the literal `cd` or `pushd` targets before it in the same command (`~` is the home directory; `cd` alone goes home); it is blocked when it sits in a `tools` directory whose parent holds the `oasis` entry point and `tools/actions.py`, which is true of the installed bundle and of an oasis source checkout, so `cd ~/.agents/skills/odoo19 && tools/menu`, `./menu` inside its `tools`, or `python3 tools/actions.py` there are blocked too. When the path cannot be known from the text (`$VAR`, globs, substitutions, `cd -`, `popd`), the script is blocked only when it is spelled `tools/menu` or `tools/actions.py` and the session works inside an oasis tree. A `tools/menu` or `tools/actions.py` of another project is not blocked. Asking only for help (`--help` or `-h` as the single argument) is allowed.
- `oasis menu --catalog` prints the same actions as JSON and runs nothing; it is the only list of actions (`tools/actions.py`), which the Gentle Shell panel reads. Each action has `id`, `group`, `label`, `kind` (`command`, or `log` for the server log), `command`, `argv`, `inputs`, `destructive`, `confirm` (`database`, `yes` or null), `user_run`, `terminal_only`, `follow` (true only for *Follow the server log*, a `log` action whose `argv` is `tail -n 200 -f <server_log>`) and `superseded_by` (the action that replaces it in the menus: `server.run` for `server.start` and `server.restart`, else null); an input also has `choices` (a closed list of `{value, label, warning}`, or null) and `default` (a choice: the value Enter takes; a text input: only shown); `argv` is a template of words and `{"input": id}`, `{"input": id, "option": "-x"}`, `{"input": id, "flag": "-x"}` and `{"compact": "--compact"}` items, filled in order (the module docstring of `tools/actions.py` gives the rules). The catalog also carries the project, the entry point, `server_log`, the checkout's modules, the `list-databases` command, `checkout` (`name`, `server` with `state`, `pid`, `port`, `database` and `error`, `default_database`, and the `no_database` warnings of `start` and `restart`) and `last` (`action`, `answers`, `label`, or null). New keys are only added (`catalog_version` stays 1), so an older panel keeps working: it lists the new action too but cannot answer its dev mode, and nothing runs.

## Gentle Shell panel

The Gentle Shell layer shows the same catalog as a pop-up panel. Press `alt+o`, or run `/oasis menu`, in a session inside an Odoo project:

- The shortcut comes from `OASIS_MENU_KEY`, read when Gentle Shell starts and on `/reload`: unset means `alt+o`, a Pi key such as `ctrl+shift+m` or `f5` replaces it, and an empty value or `off` disables it (`/oasis menu` still works). Case does not matter: the key is registered lowercased, as Pi reads key ids (`ALT+O` is `alt+o`, `alt+pageDown` is `alt+pagedown`). A value without `ctrl`, `alt` or `super` (function keys aside) would steal typing and a repeated modifier (`alt+alt+o`) never matches, so either turns the shortcut off and the session shows `oasis: OASIS_MENU_KEY="<value>" is not a usable key (for example alt+o, ctrl+shift+m or f5); the menu shortcut is off, /oasis menu still opens the panel.` `/hotkeys` lists the active shortcuts. Example: `OASIS_MENU_KEY=ctrl+shift+m gentle-shell`.
- The panel's header shows `checkout: <main or slug>`, the server of the checkout, read from its runtime state record when the panel opens (`server: running on port <port> (pid <pid>)`, `server: stopped`, or `server: unknown (<reason>)` when the record cannot be read), and `default database: <name or none>`.
- The panel lists the groups and their actions (the last action of the checkout first, as `Repeat: <label> (<short answers>)`, when there is one) and, under the list, the command of the highlighted action with its inputs as placeholders (filled for Repeat); arrows and page keys move, Enter chooses and Escape closes. Actions marked `(confirm)` ask for a typed confirmation; `(terminal only)` actions are not run.
- *Start / restart the server* lists the databases, then opens one form: the header, the answers so far, the current question (the database with its default first, `(none)` and `(type a name)`; the dev mode; the HTTP port typed over the one the command will use) and, last, the command, drawn again after every answer and wrapped, never truncated. After the port it shows the warnings (no database, reload without its packages) and Run / Cancel. Escape or Cancel runs nothing. Repeat opens it at Run / Cancel with the remembered answers.
  - A list longer than the panel shows a window that always holds the highlighted row, with `↑ <n> more` above it and `↓ <n> more` below it for the rows out of view; the header, the answers, the question and the command stay on screen. The window moves only when the highlighted row would leave it.
  - Typing in a list (database, dev mode) filters it to the options whose name contains the typed text, ignoring case; `filter: <text>` is shown above the list, backspace edits it, and the first match is highlighted. `(none)` and `(type a name)` always stay listed; with no match the form says `no match: backspace edits the filter` and highlights nothing: Enter does nothing until you move to `(none)` or `(type a name)`. Choosing `(type a name)` starts the typed name from the filter. Escape clears a filter first and cancels the form when there is none. Run / Cancel and the typed port are not filtered.
  - The command shown is the native one, the `odoo-bin` line the server will run (`<python> <odoo-bin> -c <odoo.conf> …` with the addons path, data directory, ports and the chosen options), printed by `oasis --project <root> start --print-command [options]` (`restart` likewise; `--detach` is left out, the detached server runs the same line) and read in the background whenever the answers change. It is abbreviated: the home directory is `~`, and any value longer than 40 characters (the part after `--option=`, else the whole word, such as a long addons path) keeps its first 20 and last 19 characters around `…`. While it is read, the form shows the oasis command with `(loading the odoo-bin command…)`; when it cannot be read (an older core without `--print-command`, a non-zero exit, more than one line), the oasis command with `(the odoo-bin command is unavailable: <exit N, unexpected output or could not run>; this is the oasis command)`, and nothing else changes. The full native line goes to the run's result entry (`native: <line>`).
- Inputs are asked with Pi's dialogs, in catalog order: modules from the checkout, databases from `list-databases` (the footer and a notice show `Listing databases (this may start the database service)...` while it runs), `(type a name)` to type another database, `(skip: ...)` for an optional one, and No/Yes for options such as demo data. A typed value must match the catalog's pattern (its message is shown and the question asked again) and cannot start with `-`. Escape at any question runs nothing.
- Confirmation follows the catalog and always shows the filled command: `drop-database` runs only after you type the database name, `stop --database`, `gc --apply`, `gc --apply --trash` and `migrate --apply` after you type `yes`; every other action asks Yes/No with the command (and, for the older start and restart with no database, what Odoo will use instead). Repeat asks the same.
- It runs the catalog's command as filled, never rebuilt, in the project root (`test-module` and `update-module` with `--compact`), one action at a time; the footer shows the elapsed time. *Show the end of the server log* runs `tail -n 200` on `server.log` (a notice says when there is no log yet). *Follow the server log* opens a live view instead: an overlay with the last lines of `server.log` that fit, read again every second while it is open (only the last 64 KiB of the file are read; when they hold no whole line, the end of that line is shown, starting with `…`); Escape or Enter closes it, and nothing is run or recorded. *Create a development database with role accounts* asks for passwords, so the panel only shows its command to copy into a terminal.
- After a run it remembers the action and its answers for Repeat (`runtime_state.py remember`, the same `menu.json` as the terminal menu; not for actions only the user runs); when that fails a notice says `oasis menu: could not remember this action: <reason>` and nothing else changes.
- The result appears in the conversation as an `oasis:` entry with the action, the exit status, `$ <exact command>`, for *Start / restart the server* the full native line (`native: <odoo-bin line>`, when it could be read) and the output: test and update runs summarized like `oasis_test_module` and `oasis_update_module`, other output as printed (up to 1000 lines), its last 20 lines until you expand tool output (`ctrl+o` by default). When a command cannot be started at all (for example a missing program), the entry shows the attempted command with `(could not run)` and the error, and a notice says the same. It is a custom session entry: Pi shows it and keeps it in the session file but never sends it to the model, so a panel run costs no tokens and the agent does not see it.
- Only the user opens the panel: no agent tool does, and the bash guard keeps agents from `oasis menu`. It needs the interactive terminal UI.
