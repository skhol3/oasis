# New project: deliberate setup

1. Describe the project in one **workspace file**: an `oasis-workspace.toml` at the project root, read by every checkout and linked worktree below it. [Setting up a new workspace](new-workspace.md) goes from an empty folder to a passing `doctor`, a development database and a first test run, with an annotated example tree; the keys are in [Workspace file](workspace-file.md) and the [example workspace file](../odoo19-environment/assets/oasis-workspace.example.toml). Only with authorization, fill it with the project's real paths and namespace; do not copy test fixture or example values as defaults. The `[tooling]` table is the path and namespace authority for the [tools](../tools/config.py); the optional `[development]` account declaration is consumed only by `init-dev-database`. Do not put credentials in it or inspect secret-bearing runtime files.
2. Alternatively, keep the legacy **profile**: a project-local `.odoo19-agent.toml` in each checkout, starting from the [example project profile](../odoo19-environment/assets/odoo19-agent.example.toml). It keeps working unchanged, and a checkout with a profile ignores any workspace file; [Migrating to the workspace file](migrating.md) converts existing profiles. Review the actual project's permissions and layout first, with the same rules: real paths and namespace only with authorization, no fixture values as defaults, no credentials. Other sections of the profile guide agents.
3. For direct invocation, install the bundle's `oasis` executable at `~/.agents/skills/odoo19/oasis` (owner makes it executable). `odoo19`, next to it, is a compatibility alias: the same dispatcher, with every command, option, exit code and output identical; only help and usage name the program invoked. Supply the absolute project directory explicitly; no project wrapper, PATH link, or shell configuration change is required. For example: `~/.agents/skills/odoo19/oasis --project /absolute/project check-environment --quick`. Run `~/.agents/skills/odoo19/oasis --help` without a project to see the fixed public commands. The entry point selects only packaged `tools/` commands; it does not replace the configuration guards or grant operational consent.
4. Alternatively, if the project wants legacy local CLI entrypoints and explicitly authorizes them, review the 18 [project wrapper templates](../project-wrappers/common.sh) and copy **only** the selected wrappers to its approved `dev/scripts/` directory. The tested templates derive the project root from that directory depth; another layout requires an explicitly validated adaptation. Do not overwrite existing scripts without separate approval. The wrappers locate global tools at `~/.agents/skills/odoo19/tools`; `OASIS_TOOLS_DIR` (or the legacy `ODOO19_TOOLS_DIR` when it is unset) is an explicit test/development override for wrappers, not a global entry point override. Missing installed tools fail clearly. Installing this package does not install wrappers into any project.
5. Keep project configuration, dependency inputs/locks, Compose files, environment variables, data, and runtime/virtualenv **local to the project**, never in this bundle (the [example tree](new-workspace.md#the-example-tree) keeps the Odoo source and the environments in a folder shared by the projects of one Odoo series). This bundle does not create an environment, start services, install dependencies, access external source trees, or grant permission to operate on databases. `bootstrap --apply`, full diagnostics, and database lifecycle commands need separate explicit consent; no workspace file, profile or skill discovery implies it.
