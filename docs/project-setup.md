# New project: deliberate setup

1. Describe the project in one **workspace file**: an `oasis-workspace.toml` at the project root, read by every checkout and linked worktree below it. [Setting up a new workspace](new-workspace.md) goes from an empty folder to a passing `doctor`, a development database and a first test run, with an annotated example tree; the keys are in [Workspace file](workspace-file.md) and the [example workspace file](../odoo-environment/assets/oasis-workspace.example.toml). Only with authorization, fill it with the project's real paths and namespace; do not copy test fixture or example values as defaults. The `[tooling]` table is the path and namespace authority for the [tools](../tools/config.py); the optional `[development]` account declaration is consumed only by `init-dev-database`. Do not put credentials in it. The database account lives in the env file that `oasis setup` generates (see [The database account](setup.md#the-database-account)): no oasis workflow requires reading, copying or typing a password.
2. A project configured by the per-checkout file of earlier versions is refused until it is converted: see [Migrating to the workspace file](migrating.md).
3. For direct invocation, install the bundle's `oasis` executable at `~/.agents/skills/oasis/oasis` (owner makes it executable); it is the one entry point. Supply the absolute project directory explicitly; no project wrapper, PATH link, or shell configuration change is required. For example: `~/.agents/skills/oasis/oasis --project /absolute/project doctor --environment --quick` (`check-environment --quick`, its deprecated alias, still runs the same checks). Run `~/.agents/skills/oasis/oasis --help` without a project to see the fixed public commands. The entry point selects only packaged `tools/` commands; it does not replace the configuration guards or grant operational consent.
4. Alternatively, if the project wants legacy local CLI entrypoints and explicitly authorizes them, review the 18 [project wrapper templates](../project-wrappers/common.sh) and copy **only** the selected wrappers to its approved `dev/scripts/` directory. The tested templates derive the project root from that directory depth; another layout requires an explicitly validated adaptation. Do not overwrite existing scripts without separate approval. The wrappers locate global tools at `~/.agents/skills/oasis/tools` (wrappers copied before 0.17.0 call the old install directory: `oasis doctor` lists them, see [From an earlier version](install.md#from-an-earlier-version)); `OASIS_TOOLS_DIR` (or the legacy `ODOO19_TOOLS_DIR` when it is unset) is an explicit test/development override for wrappers, not a global entry point override. Missing installed tools fail clearly. Installing this package does not install wrappers into any project.
5. Keep project configuration, dependency inputs/locks, Compose files, environment variables, data, and runtime/virtualenv **local to the project**, never in this bundle (the [example tree](new-workspace.md#the-example-tree) keeps the Odoo source and the environments in a folder shared by the projects of one Odoo series). This bundle does not create an environment, start services, install dependencies, access external source trees, or grant permission to operate on databases. `bootstrap --apply`, full diagnostics, and database lifecycle commands need separate explicit consent; no workspace file or skill discovery implies it.
