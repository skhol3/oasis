# Servers and ports per checkout

Each checkout controls only its own Odoo server; the PostgreSQL service is one and shared.

## Server records and ports

- `start` runs at most one server per checkout and records its pid, HTTP port and, when it is given with `-d` or `--database` (or an abbreviation `--datab` and longer), the database in `${XDG_RUNTIME_DIR:-/tmp}/oasis-<uid>/<16 hex of sha256(checkout path)>/server.json` (directories 0700, refused when they are symlinks or owned by another user; never inside the repository). Liveness reads `/proc`, so per-checkout servers work on Linux only: a record is live while its pid is a process of the current user whose command line is the Odoo launch (`<python> <odoo-bin> ...`, or `odoo-bin` itself as argv[0]); `<python>` is an interpreter whose name starts with `python` or the configured `python` that `start` records in `server.json` (realpaths compared, so `pypy3` or a renamed venv binary works); for 10 s after `started_at` any process with that pid counts, because `start` writes the record just before it execs Odoo. A stale or invalid record is removed when read, only if the file still holds what was read. A second `start` while the server lives exits 2 with `Odoo is already running for this checkout: pid <pid>, port <port>; run oasis stop first.` (`odoo19 stop` through the alias).
- Port: only `-p <port>`, `--http-port <port>` and `--http-port=<port>` are recognized as an explicit port (an abbreviation such as `--http-p` reaches Odoo unchecked and unrecorded); it is used as given (`Port <port> is in use by another process; pass another --http-port or stop that process.` when busy). Otherwise the main checkout, and a project outside git, use the `http_port` of `odoo.conf` (8069 when absent) and refuse a busy one with `Port <port> is in use by another process; pass --http-port or stop that process.`; when the live server record of another checkout of the current user names that port, the message names it instead: `Port <port> is in use by checkout <checkout path> (pid <pid>); pass [another] --http-port or run oasis stop in that checkout.` a linked worktree takes the first free port from `http_port + 1` to `http_port + 50`, and also the first free second port after the conf's option of the series (`--gevent-port` after `gevent_port` on 19.0, `--longpolling-port` after `longpolling_port` on 15.0; 8072 when absent; `second_port_conf_option` in `tools/odoo_versions.py`), so two servers with workers never collide. When none of the 50 is free, `start` refuses with `No free gevent port from <first> to <last>; pass --gevent-port or stop another server.` (`longpolling` and `--longpolling-port` on 15.0). Only these options (and `http_interface`, the address probed; an explicit `--http-interface <address>` or `--http-interface=<address>` wins over it, and so does any unambiguous abbreviation Odoo's option parser accepts, from `--http-i` to `--http-interfac`, in either form: `--http-int=127.0.0.2`) are read from `odoo.conf`. The chosen `--http-port=<port>` goes after the configuration options; a port the user passed is not repeated.
- A port that cannot be bound for another reason than being in use (for example a privileged port) exits 2 with `Cannot bind port <port>: <reason>.` (`permission denied`) before anything runs.
- The action menus keep their own file in the same private directory: `menu.json` (0600), the last action run from `oasis menu` or the Gentle Shell panel with its answers, and the last database of *Start / restart the server* ([action menu](action-menu.md)). `stop` removes only `server.json`, so it survives.
- Simultaneous `start` runs in different checkouts may probe the same free port before either binds it: start servers one at a time.

## Database service

- Every command that needs the database runs `compose up -d --wait <db_service>` under an exclusive `flock` of `compose-<16 hex of sha256(real path of the compose file)>.lock` (0600) in `${XDG_RUNTIME_DIR:-/tmp}/oasis-<uid>/`, so checkouts that share a compose file start the service one at a time instead of failing with Docker's container name conflict; a command that waits more than 120 s for that lock exits 1 with `Timed out waiting for another checkout to start the database service.`, and without `flock` on `PATH` it prints `WARNING: flock not found; starting the database service without the cross-checkout lock.` and runs `compose up` unlocked.
- `start-database` (v0.16.0, Tier A in the [agent policy](agent-contract.md)) starts the service that way and nothing else, then prints one line: `database service <db_service> is running (<compose file>)`. No output of it names the environment file, so an agent harness that refuses a command naming one runs it: setup's next steps, `status --json` and doctor name it. When `compose up` fails, what docker compose printed goes to stderr with the environment file's path replaced by `[tooling].env_file`, then `ERROR: the database service <db_service> did not start (exit <n>); oasis --project <checkout> doctor checks its configuration.` (exit 1); a missing compose or environment file exits 1 naming `oasis --project <checkout> setup --apply`, which creates it (the environment file by its key, `[tooling].env_file`). It takes no arguments (exit 2 with its usage). `stop --database` stops the service again.

## Starting a server

- A server started without `-d`/`--database` (or an abbreviation) whose `odoo.conf` names a `db_name` prints `WARNING: no database given (-d); Odoo will use odoo.conf's db_name (<name>).` to stderr before Odoo starts (with or without `--detach`, and through `restart` when no database is kept); the exit status and everything else are unchanged. A conf without `db_name`, or with `db_name = False` (as Odoo writes none), prints nothing. Batch runs (`--stop-after-init`) and informational options are not warned.
- Before Odoo starts, `start` prints `oasis start: http://localhost:<port> (pid <pid>)` to stderr (`odoo19 start: ...` through the `odoo19` alias). `start --help`, `-h` and `--version` go straight to Odoo: no port check, no record.
- `start --detach [odoo options]` starts the same server in the background: in a session of its own, stdin from `/dev/null`, stdout and stderr appended to the checkout's `server.log` (0600) in the compact log directory (`dev/logs/odoo19/server.log`, or `<logs>/<slug or main>/server.log` with `[tooling].logs`). It prints `pid=<pid> port=<port> log=<path>` and exits 0 once the server accepts connections on its HTTP interface: the address of `--http-interface` when given, else the `http_interface` of `odoo.conf`, and `127.0.0.1` when that is absent, empty, `0.0.0.0` or `::`. The record, the port rules, the one-server check and `stop` are the same. When the server exits meanwhile, its record is removed and `start` exits 1 with `Odoo exited at once with status <n>; the end of <log>:` followed by its last 20 lines. When nothing listens there within 30 s, the server is stopped (SIGTERM to its session, then SIGKILL 5 s later to every process of the server still running: the server first, then the members of its session and process group, and their descendants, scanned again for new ones as `stop --force` does, so a member that ignores SIGTERM or outlives the server does not stay), its record is removed and `start` exits 1 with `Odoo did not listen on <address>:<port> within 30 s and was stopped; the end of <log>:` followed by the same lines. `--detach` must be the first argument; it cannot be combined with `--stop-after-init` (exit 2). Without `--detach`, `start` is unchanged.
- `start ... --stop-after-init` (for example `start --stop-after-init -u <module> -d <database>`) is a batch run that serves nothing: no running-server or port check, no record, no banner, and like test runs a free `--http-port=<port>` and a distinct free second port (`--gevent-port=<port>` on 19.0, `--longpolling-port=<port>` on 15.0); an explicit port of either kind is passed as given, unchecked, and the other one is still added. It runs while this checkout's server serves; the database guards still apply.

## Restarting a server

- `restart [odoo options]` stops this checkout's server as `stop` does (its line is printed: `Stopped Odoo for this checkout: pid <pid>, port <port>.`, or `No Odoo server running for this checkout.`), then starts it again as `start --detach [odoo options]` (the same record, log, readiness wait and output `pid=<pid> port=<port> log=<path>`). Without an explicit `-p`/`--http-port` the new server keeps the port the stopped one had, passed as `--http-port=<port>`, and without `-d`/`--database` (or an abbreviation from `--datab`) the database its record names, passed as `-d <database>` (checked by the database guards before the server is stopped); a server started without a database, or recorded before 0.11.0, restarts without one. A checkout without a running server gets `start`'s port rules and no database. Every other option is passed only when given.
- Everything `start` would refuse is refused before the running server is touched, with `start`'s message and exit 2: a database guard, an invalid explicit port, an explicit port other than the server's that is busy (`Port <port> is in use by ...; pass another --http-port ...`), `--stop-after-init` (`restart starts a server; it cannot be combined with --stop-after-init.`); `--detach` (implied), `--version` and `--help` or `-h` with other options print `Usage: <entry point> restart [odoo options]` (exit 2). `--help` or `-h` alone prints the help.
- When the server does not stop within 20 s, nothing is restarted: `stop`'s message (which names `stop --force`) is followed by `Nothing was restarted: Odoo is still running for this checkout.` and `restart` exits 1, leaving the server and its record as they are. When `stop` fails for another reason (for example an unreadable runtime state, exit 2), its message is followed by `Nothing was restarted.` and `restart` exits with `stop`'s code; nothing is started.

## Printing the native command

- `start --print-command [odoo options]` prints the odoo-bin command line that `start` would exec, as one POSIX shell-quoted line on stdout (Python's `shlex.join`: words with spaces or quotes in single quotes), and exits 0: `<python> <odoo-bin> -c <odoo.conf> [--addons-path=<paths>] [--data-dir=<dir>] [--http-port=<port>] [<second port option>=<port>] <odoo options>`, built by the same code as a real start (configuration options, port choice and its probes, the given options in their order). For example `oasis --project /srv/shop start --print-command -d acme_dev_shop --dev xml` prints `/srv/env/bin/python /srv/odoo/odoo-bin -c /srv/shop/dev/odoo.conf --http-port=8069 -d acme_dev_shop --dev xml`. Nothing else runs: no `compose up`, no Odoo (not even `odoo-bin --version`), no server record or log, no banner and no `WARNING: no database given ...`. `odoo.conf` is never printed, and the values of the password options are printed as `***` (`-w <value>`, `-w<value>`, `--db_password` and `--smtp-password` with `=<value>` or a separate value, and their abbreviations from `--db_pa` and `--smtp-pa`; a password option takes the next word as its value, `--` included, as Odoo's option parser reads it, while words after a `--` that ends the options are not Odoo options and are printed as given). Refusals are `start`'s, with its messages and exit codes (a database guard, an invalid or busy port, a server already running for this checkout). `--help`, `-h` and `--version` print the informational command, and `--stop-after-init` the batch command with its free ephemeral ports. `--detach` may follow `--print-command` and changes nothing: the line is the one `start --detach` execs.
- `restart --print-command [odoo options]` prints the command line `start --detach` would exec for that restart, in the same format: the kept `--http-port=<port>` and `-d <database>` of the running server when not given, and the running server's HTTP and second ports counted as free, since restart stops that server first (a linked worktree's second port is read from the server's command line). Nothing is stopped or started; without a running server it prints `start`'s line. Refusals are `restart`'s (`Usage: ...` for `--detach`, `--help` with other options and `--version`).
- `--print-command` is recognized only as the first argument after the command; anywhere else before `--` both commands exit 2 with `--print-command must be the first argument.` before anything runs. After `--` it reaches Odoo as any other word. Agents may run either form: it changes nothing.

## Stopping and status

- `stop` sends SIGTERM to this checkout's server, waits up to 20 s and reports `Stopped Odoo for this checkout: pid <pid>, port <port>.` (exit 1 when it does not stop in time: `Odoo did not stop within 20 s: pid <pid>, port <port>; run oasis stop --force.`, `odoo19` through the alias, the server and its record left as they are); without a server it prints `No Odoo server running for this checkout.` and exits 0. It never stops another checkout's Odoo.
- `stop --force` does the same, then also waits up to 20 s for the other processes of the server (the members of its session and of the process group it leads, and their descendants: of the current user, started after it, never the command's own process or its parents), and sends SIGKILL to every one still running: the server first and, once it has ended, the others, so a prefork master cannot replace a worker it sees die; then the processes of the server are scanned again and new ones killed until a scan finds none (at most 10 rounds). Once the server is gone its record is removed. It reports `Killed Odoo for this checkout after 20 s (SIGKILL to its session): pid <pid>, port <port>.` when the server itself had to be killed, `Stopped Odoo for this checkout: pid <pid>, port <port>; killed <n> process(es) of its session that outlived it.` when only processes it left were, and the plain `Stopped ...` line otherwise (exit 0). A server still running 5 s after SIGKILL exits 1 with `Odoo is still running after SIGKILL: pid <pid>, port <port>.` and keeps its record. When the server's `/proc/<pid>/stat` cannot be read, its other processes are unknown: only the server gets SIGKILL, with `Killed Odoo for this checkout after 20 s (SIGKILL; its other processes could not be read): pid <pid>, port <port>.`. `--force` and `--database` cannot be combined (usage `[--database | --force]`, exit 2).
- `stop --database` stops the Compose database service (`compose stop <db_service>`) only when no other checkout has a live server; otherwise it exits 2 with `Refusing to stop the database: Odoo is running for other checkouts:` followed by one `  <checkout> (port <port>, pid <pid>)` line each.
- `status` prints `server: running pid <pid> port <port>` or `server: stopped` for this checkout (`server: unknown (<reason>)` when the runtime state cannot be read, for example a symlinked state directory; the reason is the last line the read wrote to stderr). In a git checkout it then lists the live servers of every checkout of the repository (the worktrees `git worktree list` names, main and linked, and projects inside them), by path: `repository servers: <n>`, then one `  <checkout>: pid <pid>, port <port>[, database <database>][ (this checkout)]` line each, the database when the record names one (`repository servers: unknown (<reason>)` when they cannot be read: an unreadable runtime state, or git missing or failing, for example `unknown (git worktree list failed: <git's last error line>)`; never a count of 0). Only the list read from the helper's stdout is counted; its warnings go to stderr. A project outside git prints only its own line, as before. Then `compose ps`. Warnings of a successful read go to stderr unchanged and never into the server line. No temporary file is used, so a missing or non-writable `TMPDIR` does not stop it.

### Status as JSON

`oasis status --json` (v0.16.0) prints one JSON object on one line: what is ready, what is missing and the
next command to run. It only reads (the configuration, the environment's `pyvenv.cfg`, the locks,
`docker compose ps` of the database service, this checkout's databases while the service runs, and the
server record); it never starts the service, and it also runs in a checkout without a workspace file.
A step it cannot read (a configuration or lock file it may not open, a worktree whose slug cannot be read)
is not ready with the `detail` `unknown (<reason>)`, and the output is still one JSON object (exit 0).
`status` without `--json` is unchanged.

```json
{"project": "/w/shop", "ready": ["workspace", "environment", "locks"],
 "missing": ["database_service", "databases", "server"],
 "checks": {"workspace": {"ready": true, "detail": "/w/shop/oasis-workspace.toml"},
            "environment": {"ready": true, "detail": "/w/shop/.oasis/venv"},
            "locks": {"ready": true, "detail": "current"},
            "database_service": {"ready": false, "detail": "stopped"},
            "databases": {"ready": false, "detail": "unknown while the database service is stopped"},
            "server": {"ready": false, "detail": "stopped"}},
 "next": "oasis --project /w/shop start-database"}
```

| Check | Ready when | `next` when it is the first one missing |
| --- | --- | --- |
| `workspace` | the configuration loads (`detail`: the workspace file, or why not) | `setup --plan --json` without a workspace file, `doctor` when it does not load |
| `environment` | the environment has a `pyvenv.cfg` and its Python | `bootstrap --apply` |
| `locks` | `lock.sha256` matches (`detail`: `current`, `missing`, `stale`, `edited`, `unknown (<reason>)`) | `bootstrap --apply` (`doctor` for `edited` and `unknown`) |
| `database_service` | `docker compose ps` shows it running, and healthy when it has a health check (`detail`: `running`, `starting`, `unhealthy`, `stopped`, `unknown (<reason>)`) | `start-database`, which starts it (and waits until it is healthy), for `stopped` and `starting`; `doctor` for `unhealthy` and `unknown` |
| `databases` | a development database of this checkout exists (`detail`: this checkout's managed databases, or `unknown (<reason>)`) | `init-dev-database <module> <dev_prefix>manual` with `[development]`, else `install-module <module>` (the first module of the addon roots; `create-database <name>` without modules); `doctor` when they cannot be read |
| `server` | this checkout's server runs (`detail`: `running pid <pid> port <port>`) | `start` |

`next` is `null` when everything is ready, and a shell-quoted command line otherwise (Python's `shlex.join`:
a checkout path with spaces or quotes is quoted). Every command is `oasis --project <checkout> ...` (`odoo19`
through the alias). The database service gets `start-database` rather than `list-databases`: `list-databases`
starts the service too, but the [agent policy](agent-contract.md) lists it as one that only reads and reports;
and rather than the `docker compose ... up -d --wait` it runs, which names the environment file. With the
`[development]` table setup writes in a new workspace, `databases` is followed by `init-dev-database`.

Earlier behaviour of `stop` and of the test databases is recorded in the [changelog](../CHANGELOG.md) (0.3.0, 0.4.0 and 0.8.0, under Changed).
