# Changelog

All notable changes to oasis are recorded here. The format follows Keep a Changelog
(`keepachangelog.com`) and versions follow Semantic Versioning (`semver.org`).

While the version is `0.x`, the contract (the `oasis` and `odoo19` command names and
options, the `.odoo19-agent.toml` `[tooling]` keys, the database prefix guards and the skill
names) may still change in a minor release; every such change is listed here under **Changed**.

## [Unreleased]

### Added

- Credentials generated by oasis (S2): `oasis setup` writes the database account to a new environment file
  (mode 0600): `ODOO_DB_USER=oasis_<name>` and a random `ODOO_DB_PASSWORD`, or the `db_user` and
  `db_password` a kept `odoo.conf` sets. The compose service and Odoo both read that one file; `odoo.conf`
  stays password-free. Every command that starts Odoo passes the account as `PGUSER`/`PGPASSWORD` in the
  environment, never on its command line, and only what `odoo.conf` leaves unset. No password is printed,
  and no oasis workflow requires reading, copying or typing one.
- `doctor` and `check-environment --full` check `postgres_connection` with the account Odoo uses, over the
  `db_host`/`db_port` of `odoo.conf`, using the environment's Python and psycopg2. A refused account FAILs
  with its fix: either `odoo.conf` values that differ from the environment file, or the volume recreate below.
- New Tier B command `recreate-database-volume --confirm <compose project>`: deletes the PostgreSQL volume of
  the compose project (every database in it, the trash included) and starts the service again with the
  account of the environment file. It replaces a raw `docker compose down -v`. Without the exact compose
  project it prints the plan, changes nothing and names the exact command.
- Agent contract (S1): one policy table in the core (`tools/policy.py`) lists every operation, its tier
  (A: the agent alone; B: the agent proposes, a person confirms; C: a person only), why, and what
  `--confirm` takes. `oasis policy --json` (and `odoo19 policy --json`) prints it from any directory,
  also without a workspace file or in a checkout with a legacy profile. docs/agent-contract.md and the
  bash guard's tier table are generated from it.

### Changed

- `oasis setup` respects an existing env file: it fills only account variables present with an empty
  value (files from older setups), in place, every other byte kept, mode 0600; a file that sets
  neither `ODOO_DB_USER` nor `ODOO_DB_PASSWORD` is left unchanged with a WARN saying how to opt in. It
  moves `db_user`/`db_password` out of a kept `odoo.conf` (those lines only) only when the env file
  holds the same values; otherwise it warns and changes nothing.
- `oasis doctor`: `WARN odoo_conf_password` (fix: `oasis setup --apply`), `WARN env_file=unassigned`,
  `env_file=empty` names `oasis setup --apply`, and `FAIL env_file=unsupported_value <names>` for values
  using compose interpolation (`$`) or double-quoted escapes (`\`), which oasis refuses instead of passing
  Odoo another credential (`check-environment` fails the same way). The authentication-failure fix names
  `recreate-database-volume` only when `odoo.conf` points at the port the compose service publishes.
- `init-dev-database` no longer needs a terminal: passwords are generated into `<database>.logins` next
  to the env file (mode 0600, never printed); on a terminal Enter generates one and typing your own
  still works.
- `recreate-database-volume` always runs with `-p <compose project>`, refuses a `COMPOSE_PROJECT_NAME`
  that selects another project, and on a failure after `down -v` names the command that starts the
  service again (exit 1).
- `oasis setup` no longer asks you to fill in the database account; its next steps start with starting the
  database service. `doctor` makes one connection: the `postgres_connection` login check (WARN when the
  service does not answer).
- Contract change: Tier B in the CLI. `drop-database <name>`, `gc --apply --trash`, `migrate --apply`
  and `worktree-init` run only with `--confirm <exact name>` (the database name, the project root, the
  workspace file the plan writes, the worktree path the plan names). Without it, or with another value,
  they change nothing, exit 2 and name the exact command to run. `worktree-init --dry-run`,
  `migrate --plan` and resuming an existing worktree need no confirmation. The menu (Move a database to
  the trash, Empty trash, Migrate, Create a linked worktree, which now asks for the absolute folder),
  `/oasis worktree` and `/oasis migrate` pass it after the user's confirmation.
- Contract change: the Gentle Shell bash guard takes its tiers from the policy table
  (`pi/lib/policy.generated.ts`, checked against it by the tests). Agents may now run `setup --apply`,
  `migrate` without `--apply` and `worktree-init --dry-run` (Tier A). `worktree-init` and
  `migrate --apply` (Tier B) now wait for the user's confirmation in a dialog, honoring
  `[tooling].agent_destructive`, like `drop-database`; before, they were blocked in every session. An
  oasis command whose arguments are not literal gets its strictest tier. `stop --database` stays Tier B
  (it ends the sessions of a running server on the shared database). The skills treat `gc --apply` as
  Tier A.
- The refusal of a legacy `.odoo19-agent.toml` and `doctor`'s fix name runnable commands:
  `oasis --project <checkout> migrate --plan`, then the exact
  `oasis --project <checkout> migrate --apply --confirm <workspace file>` (the file the plan writes),
  or only the plan when migrate cannot plan.
- Bash guard: an abbreviated or `=` form of a Tier B option (`migrate --ap`, `stop --datab`,
  `gc --apply --tr`) asks like the full option; an entry point whose command word is not known from
  the text gets the strictest row of any oasis command word on the line. `oasis policy` has its own
  row (Tier A).
- The Gentle Shell prompt context points to `oasis policy --json` for the Tier B commands.

### Removed

- The unenforced statement that agents may not read environment files; replaced by the guarantee that no
  oasis workflow requires reading, copying or typing a password.

### Fixed

- The generated database user name strips `_dev_` only when it is there.
- `worktree-init` names `git worktree prune` when a prunable worktree entry (its folder gone) holds
  the target branch, instead of saying the branch is checked out there (S4.9).
- `check-environment --full` and `bootstrap` no longer report `FAIL dependency_audit=failed` on an
  environment whose Python is older than 3.10 (Odoo 15: 3.7 to 3.9): the dependency audit works out
  which distribution provides each module from the installed distributions and the standard-library
  names from the interpreter itself. On 3.10 and later its output is unchanged.
- `oasis_test_module` and `oasis_test_summary` read the Odoo 15 result line (logger
  `odoo.tests.runner`): Odoo 15 runs no longer report `result: not reported`, and a failing run's
  result line is no longer counted as a problem. A run in which no test ran adds
  `no tests ran: the run only installed <module>` (`updated` in reuse update mode).

## [0.15.1] - 2026-11-26

### Fixed

- The bash guard now checks every Gentle Shell tool that runs shell text: `bash_background` and
  `monitor` get the same decision as `bash` for the same command (deny, the ask dialog with
  `[tooling].agent_destructive`, or allow), also when a `codemode` script calls them. Before, a
  denied command such as `oasis setup --apply` ran unchecked through `bash_background`.

## [0.15.0] - 2026-11-25

### Added

- `oasis setup --environment <dir>` adopts an existing Python environment (a `pyvenv.cfg` whose
  `version` is a Python the series supports, read and never run) for a new workspace or a new
  `[series."x.y"]` section; setup never creates, syncs or deletes it, and the next steps say that
  `bootstrap --apply` syncs it to the locks. `[series."x.y"]` sections accept `python`
  (`'3.<minor>'`, within the series' range) for the environment the section or `[tooling]` gives.
- `overrides.txt` in a requirements directory is an optional lock input: `uv pip compile` gets
  `--override overrides.txt`, `lock.sha256` records it, and adding, changing or removing it makes
  the locks stale. Without it, the locks, the compile commands and the messages are unchanged.
  When setup adopts a series folder with `requirements-extra.txt` or `requirements-overrides.txt`,
  a new `runtime.in` includes the first and a new `overrides.txt` the second; those files are never
  copied or edited.
- `oasis setup` in a checkout of an Odoo series the workspace file has no section for (a 15.0
  branch of a 19.0 project) adds a `[series."x.y"]` section to that file (a `workspace_version = 1`
  file becomes version 2, that line only) and the machine file entry of the series, and creates
  only that series' missing files: `config/<x.y>/` by default, `logs/<x.y>` and `data/<x.y>`,
  prefixes `<name><major>_dev_` and `<name><major>_test_`, PostgreSQL of the series on a port no
  other series uses, the series' Python. A folder that already holds the series' files
  (`config/odoo-15/`, or `--config-dir <dir>`) is adopted; `--exception <module>` (repeatable)
  writes `series_exceptions`. A file that cannot be extended without changing another series is
  refused (docs/setup.md#another-odoo-series).
  A kept `odoo.conf` or compose file whose PostgreSQL port another series uses is refused, naming
  both series, the port and the fix. A failed verification, `uv pip compile` or `uv venv` undoes
  every change, including the workspace file edit, the machine entry and rewritten locks.
  The adopted folder keeps that series' data and logs where they are: the `data_dir` of its kept
  `odoo.conf` (only that option is read) becomes the section's `data_dir`, and an existing
  `logs/<folder name>` inside the workspace (`logs/odoo-15` for `config/odoo-15`) becomes its `logs`.
- Odoo 15.0 in the series table (`tools/odoo_versions.py`), read from the 15.0 source: Python
  3.7-3.12 (default 3.10), PostgreSQL 12 minimum and 14 by default, `--longpolling-port` as the
  second port (after the odoo.conf `longpolling_port` in a linked worktree), no demo data with
  `--without-demo=all` (the 15.0 option takes a value), demo data by default (no `--with-demo`),
  the `--test-tags` class filter, and the `--dev` features ipdb, pdb, pudb, wdb, qweb, reload,
  werkzeug and xml (`all` = pdb, reload, qweb, werkzeug, xml).
- Series keys `demo_on_args`, `user_groups_field` and `second_port_conf_option`:
  `install-module --with-demo`, `init-dev-database` (demo options, the `res.users` groups field:
  `group_ids` on 19.0, `groups_id` on 15.0) and a linked worktree's second port take them from the
  table. `view-info` ranks `tree` views (15.0) with list views.
- `workspace_version = 2`: one `oasis-workspace.toml` for several Odoo series. `[tooling]` holds the
  shared keys and its paths may use `{series}`; `[series."<x.y>"]` sections override what differs
  (source, environment, odoo.conf, env file, compose file, requirements, db service, prefixes,
  test database, logs, data). A checkout's series comes from `odoo_version` in its
  `oasis-checkout.toml`, else its module manifests, else the workspace `odoo_version`; a series
  without a section is refused, naming `oasis setup`. Every value `tools/config.py` emits follows
  the checkout's series, so all tools do too.
- `series_exceptions` in a series section: modules the series guard and series detection ignore
  (e.g. `report_xlsx` declaring 16.0 in a 15.0 branch).
- `doctor` (version 2): `PASS series=<x.y> from=<checkout|manifests|workspace>`,
  `PASS series_exceptions=<modules>`, and `PASS|FAIL series_isolation` when two series share a
  database port, compose project, prefixes or env file, each with a fix.

- `oasis setup` asks for the Python environment it would create (a new workspace, or a new
  `[series."x.y"]` section) on a terminal, in the plan and with `--apply`: Enter creates it, or the
  absolute path of an existing environment adopts that one exactly as `--environment` does. For a
  new one it asks its Python among those the series supports, the default marked (`[Enter: 3.10]`).
  Without a terminal nothing is asked and the plan is unchanged. End of input at a question refuses
  (exit 2), Ctrl-C stops with `ERROR: Interrupted at a question: nothing changed.` (exit 130).
- `oasis setup --python <x.y>`: the Python of the environment setup creates, without asking.
  Refused when the series does not support it, with `--environment`, when the environment already
  exists, and in an already configured checkout.

### Changed

- Odoo 15.0's default Python is 3.9, the Python of Odoo's official 15.0 Debian package
  (`setup/package.dfdebian`: `debian:bullseye`; 19.0 stays 3.12, `ubuntu:noble`). A 15.0 workspace
  that declares no `python` now expects 3.9; declare `python` to keep another one.
- The `runtime.in` that `oasis setup` writes for 15.0 also requires `setuptools<81`: Odoo 15 imports
  `pkg_resources` without listing setuptools, so a uv environment could not start it and `uv pip
  sync` removed setuptools from an adopted one. docs/setup.md "Odoo 15.0 requirements" also covers
  `python-ldap==3.4.4` for OpenLDAP 2.6.
- An `oasis-checkout.toml` with a key it may not set is refused with `oasis-checkout.toml may only
  set odoo_version, [tooling].checkout_slug and [tooling].environment: <key>`.
- The menu's start / restart flow takes the dev mode option and choices from the series table.
- Unsupported-series messages list every supported series (`supported: 19.0, 15.0`); the series
  guard's fix for a module of a supported series points to the series model (`run oasis setup to
  add a [series."<x.y>"] section to <workspace file>`, or `odoo_version` in oasis-checkout.toml
  when the section exists). `oasis-checkout.toml` accepts a top-level `odoo_version`.
- The agent's changes to a checkout's `oasis-checkout.toml` ask the user in the same dialog as the
  workspace file, whatever `[tooling].agent_destructive` says; its dialog says it sets
  `checkout_slug`, the database namespace, and the environment.
- 19.0 command lines, the 19.0 menu catalog and version 1 workspace output are unchanged.

## [0.14.0] - 2026-11-25

### Added

- `oasis doctor` prints `  fix: <command or action>` after every FAIL line (for example `oasis
  setup --apply`, `oasis bootstrap --apply`, `fill ODOO_DB_PASSWORD in <env file>`); existing lines
  and `doctor_failures` are unchanged.
- `oasis doctor` shows where the layered values came from (`odoo_source_from=`,
  `enterprise_source_from=`, `project_environment_from=`, `checkout_slug_from=`, with
  `machine:<file>`, `workspace:<file>`, `checkout:<file>` or `derived`), and fails
  `env_file=empty <names>` when `ODOO_DB_USER` or `ODOO_DB_PASSWORD` is empty (names only, never
  values) or `env_file=unreadable`.
- Series guard: a checkout whose module manifests declare a series-style version
  (`<series>.x.y.z`) of another series than `odoo_version` is refused by every command (exit 2,
  naming the module, both series and the fix); `doctor` reports it as `FAIL module_series=...`.
  Manifests without such a version are ignored.
- `postgres_default` in `tools/odoo_versions.py` (17 on 19.0); `oasis setup` writes that image.
- `oasis setup` configures a checkout in one command (docs/setup.md). Without `--apply` it prints
  the plan and changes nothing (`--plan` asks for it explicitly); `--apply` creates only what is
  missing and keeps every existing file: the machine file's `[series."<x.y>"]` entry with the
  Odoo source (never edited once it exists), `oasis-workspace.toml` without source keys, a
  path-free `odoo.conf`, a compose file with PostgreSQL on a free port, the environment file with
  the variable names only (empty, 0600, never printed), `runtime.in` and `dev.in`, the locks and
  the uv environment, then prints the next steps. It infers the series from the module manifests
  and the source from the machine file, asks only on a terminal, and every answer has a flag
  (`--series`, `--community`, `--enterprise`/`--no-enterprise`, `--workspace`, `--name`). Without
  a workspace file, the workspace is the checkout itself (`oasis-workspace.toml` and `.oasis/`,
  listed in `.git/info/exclude`, never `.gitignore`); an existing workspace file is adopted. It
  rolls back if the result does not load. It runs without a workspace file, like `doctor`, which then reports `FAIL configuration=...`
  with `fix: oasis setup --apply`.
- Gentle Shell: agents may run `oasis setup` (the plan); the bash guard blocks `setup --apply` and
  any `setup` whose arguments it cannot read literally, like `migrate --apply`.
- A linked worktree with no `oasis-workspace.toml` at or above it reads the workspace file its
  main checkout reads, found through git (`git rev-parse --git-common-dir`), so worktrees can live
  anywhere; the slug still comes from the worktree's directory name, the upward search still
  comes first, and the file is trusted like any other. Gentle Shell's project detection resolves
  the same root and workspace.
- `worktree-init --path <dir>` creates the worktree at any absolute path (default unchanged:
  `<main>-<feature>` next to the main checkout); it refuses a path inside the Odoo source or
  another checkout, an existing directory that is not empty, and a folder below another
  workspace file.
- Optional machine file `$XDG_CONFIG_HOME/oasis/config.toml` (else `~/.config/oasis/config.toml`),
  the default place for each series' Odoo source: `[series."19.0"]` with `community`,
  `enterprise` and `environments`. A workspace's `[tooling].community` or `[tooling].enterprise`
  overrides it, and `enterprise = false` turns a machine Enterprise off. Checked like the
  workspace file (owner and mode, invalid TOML, unknown keys); without it everything works as
  before.
- `tools/config.py --origins <checkout>` prints where the layered values came from
  (`MACHINE_FILE`, `MACHINE_ENVIRONMENTS_DIR`, `ODOO_SOURCE_FROM`, `ENTERPRISE_SOURCE_FROM`,
  `PROJECT_ENVIRONMENT_FROM`, `CHECKOUT_SLUG_FROM`).
- `--project` is optional for `oasis` and `odoo19`: without it, the project is the git top level
  of the current directory (the current directory outside git).
- `bootstrap --apply` compiles the dependency locks when they are missing or stale against
  `runtime.in` and `dev.in` (`uv pip compile --python-version <declared Python>`, then
  `lock.sha256` as `sha256sum` writes it), then creates or syncs the environment as before.
  `bootstrap --preview` names the step (`locks=missing|stale`,
  `planned_action=compile_locks_then_...`) and changes nothing. Current locks stay
  byte-identical; the `.in` files are never written.

### Changed

- Documentation: docs/new-workspace.md starts from a clone with `oasis setup` (plan, `--apply`,
  fill the account, start the database, `doctor`, `init-dev-database`), explains the machine,
  workspace and checkout files, worktrees through git and the environment rule, and keeps the
  series-folder tree as one possible layout plus the steps by hand; the README five-minute start
  uses setup; docs/workspace-file.md describes the series guard fast path.
- `oasis setup` gives a new `odoo.conf` or compose file the port of the one it keeps, reports
  kept files whose ports disagree, and refuses `--no-enterprise` only when the machine entry has
  Enterprise.
- `bootstrap --apply` compiles the locks through `tools/locks.py compile`, the code `oasis setup
  --apply` uses; its output and messages are unchanged.
- The Python environment may be any directory that is an environment (has `pyvenv.cfg`) or does
  not exist yet; it no longer has to be inside the checkout or under a directory named
  `*environments`. It still may not be or contain the checkout or the Odoo source. `Unsafe tooling
  environment target.` now names the directory and the reason.
- An existing environment directory without `pyvenv.cfg` (an empty `mkdir`, a conda environment)
  is now refused, where the old rule accepted it under an `*environments` parent; `bootstrap` or
  `uv venv` creates the environment.
- `worktree-init` no longer requires the new folder to be below the workspace directory. It
  refuses an `oasis-workspace.toml` the main checkout tracks in git: each worktree would check out
  and read its own copy; untrack it or keep the workspace file above the checkouts.
- Bash guard: after `builtin cd`, `command cd`, `time cd` (also with `--` or `time -p`), `eval`,
  `source`/`.` or a non-literal command word, an entry point run without `--project` targets an
  unknown directory (ask). Only `command`'s own `-v`/`-V` count as a lookup, not a later `-v`.
- Bash guard: the agent's changes to the workspace file a linked worktree reads through git, and
  to the machine file (`$XDG_CONFIG_HOME/oasis/config.toml`, `~/.config/oasis/config.toml`), go
  through the same always-ask dialog as a workspace file above the session, whatever
  `agent_destructive` says.
- A workspace without `[tooling].community` whose machine file gives no source for its series
  stops with `No Odoo source for <series>: create the machine file <path> with community under
  [series."<series>"], or set [tooling].community in <workspace>.` instead of `Invalid tooling
  path: community.`
- `bootstrap` no longer refuses a stale `lock.sha256` with `Regenerate the locks and fingerprint
  before preview or apply.`; it compiles instead. A lock changed by hand while the inputs still
  match is still refused (exit 2), now with how to fix it. Without uv, `bootstrap` says how to
  install it.
- The Gentle Shell bash guard judges an entry point run without `--project` against the
  directory it runs in (the session's, a literal `cd`/`pushd`, `env -C`, `sudo -D`); an unknown
  directory counts as ask. `sudo --chdir <dir>` is parsed as taking a value.

### Fixed

- A configuration file that is not valid UTF-8 gives `Invalid TOML in <file>.` instead of a
  traceback.

## [0.13.0] - 2026-11-24

### Added

- `start --print-command [odoo options]` and `restart --print-command [odoo options]` print the
  odoo-bin command line the command would exec (python, odoo-bin, `-c`, addons path, data dir,
  the chosen ports and the given options) as one shell-quoted line on stdout and exit 0, without
  side effects: no database service, no Odoo run (not even `odoo-bin --version`), no record, no
  log. `restart --print-command` includes the port and database it would keep and counts the
  running server's ports as free. `odoo.conf` is never printed and password option values show
  as `***`. `--print-command` must be the first argument: elsewhere before `--` both commands
  exit 2 with `--print-command must be the first argument.` instead of passing it to Odoo (and,
  for restart, stopping the server).
- Gentle Shell: typing `/oa` or `/odoo` (before the space) suggests `/oasis <subcommand>` and
  `/odoo19 <subcommand>` with their descriptions; no new command names.
- Gentle Shell panel: typing in a list of the start / restart form filters it (substring,
  case-insensitive; `filter: <text>` shown, backspace edits it, Esc clears it before cancelling);
  `(none)` and `(type a name)` stay listed; with no match nothing is highlighted, so Enter does
  nothing until you move to one of them.
- Gentle Shell panel: the start / restart form shows the native `odoo-bin` line (from
  `--print-command`), abbreviated (home as `~`, values over 40 characters shortened with `…`),
  falling back to the oasis command with a note while it loads or when it cannot be read; the
  full line is added to the run's result entry (`native: …`), never sent to the model.

### Changed

- README and Install or update: oasis is described as an Odoo development harness, with 19.0 the
  supported series today; the `odoo19` names (install directory, skills, CLI alias) stay until a
  second series is supported. A table says which install does what: `./install.sh` installs the
  skills and the `oasis` CLI into `~/.agents/skills/odoo19` for any agent and the terminal; the
  Gentle Shell package (`gentle-shell install git:github.com/skhol3/oasis@<tag>`) adds the
  `oasis_*` tools, `/oasis` and the panel. Install examples use `<tag>` instead of the stale
  `v0.11.0` and show how to move between tags.

### Fixed

- Gentle Shell panel: the start / restart form's list scrolls: it shows a window around the
  selected row with `↑ n more` / `↓ n more` markers, keeping the header and the command visible
  (with many databases the selector was out of view).
- `/oasis setup` in a session Gentle Shell did not start no longer writes the subagent overlay:
  it reports `oasis setup: the subagent overlay applies only to Gentle Shell, and this session is
  not running in it; nothing written.`, and the session-start overlay reminder is not shown
  there. Gentle Shell is recognised by `PI_PROGRAM_STATUS_APP=gentle-shell`, which its launcher
  sets, or an absolute `GENTLE_PI_CONFIG_HOME`.

## [0.12.0] - 2026-11-24

### Added

- Action menu (`oasis menu` and the Gentle Shell panel): a header with the checkout (`main` or
  the worktree slug), its server state and the default database.
- *Start / restart the server*: one action that asks the database (default: the last one it used
  in this checkout, else the development database of the checkout's only module), the dev mode (a
  closed list from the series table: off, all, each feature, reload,xml) and the HTTP port, then
  shows the exact command (`start --detach`, or `restart` when the server runs) and asks to
  confirm. It warns when no database is chosen and when reload cannot work because the
  environment has neither inotify nor watchdog.
- Repeat last action: the last action run from either menu in this checkout is offered first (`r`
  in the terminal, the first row in the panel), with the same preview and confirmation; it is
  kept in `menu.json` in the checkout's private runtime directory and survives `stop`.
- `start` without a database prints `WARNING: no database given (-d); Odoo will use odoo.conf's
  db_name (<name>).` to stderr when odoo.conf names one; the exit status is unchanged.
- Catalog: `checkout`, `last`, and per-action `superseded_by` and per-input `choices` keys;
  `catalog_version` stays 1.
- `tools/odoo_versions.py` declares the dev features per Odoo series (`dev_option`,
  `dev_features`, `dev_all`, `dev_reload_packages`). 19.0: `--dev` takes access, qweb, reload,
  replica and xml; `all` turns on access, qweb, reload and xml; reload needs inotify or watchdog.

### Changed

- `oasis migrate` on a checkout that is already migrated says what configures it: `nothing to
  migrate: <checkout> has no .odoo19-agent.toml; it is already configured by <workspace file>`
  (still exit 0). A legacy profile it cannot read is refused naming the file: `Cannot read
  <profile>: <reason>.`, `Invalid TOML in <profile>.` or `Invalid tooling configuration:
  <profile> has no [tooling] table.` (exit 2).
- In Gentle Shell without git (or when git's top level is outside the workspace directory), the
  project root is the nearest directory holding `.git` below the workspace file, else the
  session directory; a leftover `.odoo19-agent.toml` between the workspace and the checkout no
  longer becomes the root.
- Gentle Shell: a profile above the checkout no longer stops the search for

## [0.11.0] - 2026-11-24

Safer destructive operations and server control: dropped databases go to a trash, agents are asked
before destructive commands under a setting the user owns, and the server can be restarted,
force-stopped and followed from the menu.

### Added

- `trash` (new command): lists the checkout's trash, one `trash <name> original=<name>
  dropped=<UTC time> age=<d>d<hh>h size=<size>` line per entry, then `trashed=<n>`; `trash restore
  <trash name>` renames the database and its filestore back, refused when the original name or
  its filestore path exists, with open sessions (exit 3), or when the name is not a trash entry
  of this checkout. See `docs/trash.md`.
- `gc --trash [--older-than <days>]` lists the trash entries dropped at least `<days>` days ago
  (0 to 36500, default 7; other values print the usage, exit 2, before any query); with `--apply`
  it drops them and their filestores (`dropped=<n>`, `failed=<m>`). A database dropped whose
  filestore cannot be removed counts as failed, and stderr names the filestore path to remove by
  hand. Plain `gc` and `gc --apply` are unchanged and never touch the trash.
- Action menu and panel: *List trash*, *Restore from trash* and *Empty trash* (`gc --apply
  --trash`, typed `yes`).
- Gentle Shell ask tier: before the agent's `drop-database <name>`, `stop --database` or `gc
  --apply --trash` (through `oasis`, `odoo19` or oasis's tool scripts) runs, a dialog shows the
  exact command and asks the user to type the database name or `yes`. A wrong answer, Esc, no
  answer within 2 minutes or a session without a dialog (subagent, headless) blocks it with a
  reason that tells the agent to ask the user; `drop-database` needs a literal database name.
  Each decision is recorded as an *Agent command approved/refused* session entry that is never
  sent to the model. The deny tier is unchanged. See `docs/bash-guard.md`.
- The ask tier also covers the files that hold `[tooling].agent_destructive`: Pi `edit` and
  `write` tool calls and bash writes (redirection, `tee`, `sed -i`, `mv` or `cp` onto it) to an
  `oasis-workspace.toml` or `.odoo19-agent.toml` in the session's directory or above it show a
  dialog that names the file (type `yes`); no dialog blocks them. The prompt context names the
  commands that ask the user. The workspace and profile examples document `agent_destructive`.
- `[tooling].agent_destructive` (`ask`, the default, `deny` or `allow`) in the workspace file or
  the profile decides that tier: `deny` blocks those commands, `allow` runs them without a dialog.
  `oasis-checkout.toml` refuses it; an invalid value fails with `Invalid tooling
  agent_destructive: use ask, deny or allow.` `tools/config.py` prints it last as
  `AGENT_DESTRUCTIVE=<value>`.
- `restart [odoo options]` (new command): stops this checkout's server as `stop` does, then starts
  it as `start --detach [odoo options]`, keeping the port the stopped server had unless the options
  name one (`-p`, `--http-port`), and the database its record names unless they name one (`-d`,
  `--database`); a server started without a database restarts without one. What `start` would refuse (database guards, an invalid or busy
  explicit port, `--stop-after-init`; `--detach` and informational options print the usage) is
  refused before the server is stopped (exit 2); a server that does not stop is left running and
  `restart` exits 1 after `stop`'s message with `Nothing was restarted: Odoo is still running for
  this checkout.`; any other failure of `stop` (an unreadable runtime state, exit 2) prints its
  message and `Nothing was restarted.` with `stop`'s exit code. See `docs/servers-and-ports.md`.
- `stop --force`: after the graceful 20 s, SIGKILL to the server and every process of it still
  running (the members of its session and of the process group it leads, and their descendants;
  never the caller or its parents), then the record is removed: `Killed Odoo for this checkout
  after 20 s (SIGKILL to its session): pid <pid>, port <port>.`, or `Stopped ...; killed <n>
  process(es) of its session that outlived it.` when only those were left. The server gets SIGKILL
  first, so a prefork master cannot replace a worker it sees die, and its processes are scanned
  again until no new one appears. When the server's process list cannot be read, only the server
  is killed (`Killed Odoo ... (SIGKILL; its other processes could not be read): ...`). A server
  still running 5 s after SIGKILL exits 1 with `Odoo is still running after SIGKILL: pid <pid>,
  port <port>.` and keeps its record.
- `status` in a git checkout lists the live servers of every checkout of the repository after its
  own line: `repository servers: <n>` and one `  <checkout>: pid <pid>, port <port>[, database
  <database>][ (this checkout)]` line each. A project outside git prints only its own line, as
  before. `start` records the database it is given with `-d`/`--database` for that list. When git
  cannot list the worktrees (missing, failing), it prints `repository servers: unknown (<reason>)`
  instead of a count; warnings of the read go to stderr and are never counted as servers.
- Action menu and panel: *Restart the server* (optional database) and *Follow the server log*
  (`tail -n 200 -f` until Ctrl+C in the terminal menu; in the Gentle Shell panel a live overlay
  that reads the end of `server.log` again every second while open; a last line longer than the
  64 KiB it reads shows its end, starting with `…`). The panel header shows the
  checkout's server: `server: running on port <port> (pid <pid>)`, `server: stopped` or `server:
  unknown (<reason>)`. The catalog's actions carry a `follow` key (true only for the live log).
- Gentle Shell: `restart`, `stop --force` and `status` stay in the allow tier (they act on the
  checkout's own server).

### Changed

- `drop-database` moves the database to the trash instead of dropping it: it prints the plan
  (`database=`, `size=`, `sessions=`, `filestore=` or `none`, `trash=`), then renames the
  database to `<name>_trash_<YYYYMMDD>_<HHMMSS>` (UTC; a name over 63 bytes keeps its first 34
  bytes plus `_<6 hex of its SHA-256>`) with the comment `oasis-trash original=<name>`, and its
  filestore directory under the data dir with it. It prints `Database moved to trash: <name> ->
  <trash name>` instead of `Database dropped: <name>`. A missing database, the usage, the
  session refusal (exit 3) and `--terminate` are unchanged. The menu action is now *Move a
  database to the trash*.
- `doctor` prints `PASS agent_destructive=<value>` after `odoo_version` when the configuration
  loads.
- `stop`: when Odoo does not stop within 20 s the message names the remedy: `Odoo did not stop
  within 20 s: pid <pid>, port <port>; run oasis stop --force.` (`odoo19` through the alias). The
  exit status stays 1.
- Contract: names ending in `_trash_<8 digits>_<6 digits>` are reserved for the trash; every
  command that takes a database refuses them (exit 2), `drop-database` and `module-status`
  included. The `gc` usage line names `--trash`.
- `start --detach` waits for the server on its HTTP interface (`--http-interface`, else the
  `http_interface` of `odoo.conf`; `127.0.0.1` for none, empty, `0.0.0.0` or `::`) instead of
  always `127.0.0.1`, for up to 30 s instead of 10 s. A server that does not listen in time no
  longer counts as started: it is stopped (SIGTERM to its session, SIGKILL 5 s later), its record
  is removed and `start` exits 1 with `Odoo did not listen on <address>:<port> within 30 s and was
  stopped; the end of <log>:` and the last lines of its log. An explicit `--http-interface` is
  also the address the port check probes.
- Messages name the remedy (exit codes unchanged): `Odoo is already running for this checkout:
  pid <pid>, port <port>; run oasis stop first.`; a busy port says `Port <port> is in use by
  checkout <path> (pid <pid>); pass [another] --http-port or run oasis stop in that checkout.` when
  another checkout's live server record names it, else `Port <port> is in use by another process;
  pass [another] --http-port or stop that process.`; a wrong Odoo runtime prints `Odoo runtime
  <series> is required; <odoo-bin> reports: <its version>.` and `Point [tooling].community at an
  Odoo <series> source, then check it with oasis doctor.`; an existing disposable name prints
  `Disposable test database already exists: <name>; it was left as it is.` and `Run the command
  again for a new name; oasis gc --apply drops what interrupted runs left.` (`odoo19` through the
  alias).
- Gentle Shell ask tier: the mode is the stricter (`deny` over `ask` over `allow`) of the session
  project's `[tooling].agent_destructive` and that of the project the command targets (the entry
  point's `--project <dir>`, or `OASIS_PROJECT_ROOT`/`ODOO19_PROJECT_ROOT` assigned before a tool
  script). A target that is not literal, not an Odoo project, unreadable or set elsewhere on the
  line counts as `ask`; a refusal by the target names it. Before, `oasis --project <other>
  drop-database <name>` from an `allow` project skipped the other project's `ask` or `deny`.
- Prompt context: the `oasis_test_module` line says that full logs stay on disk and the
  `oasis_test_summary` line to pass what `test-module --compact` printed (lost when the section
  was shortened); other lines were shortened to stay under 1200 characters.

### Fixed

- Bash guard: a line is judged on every command it holds. Outside an Odoo project, `psql -l;
  oasis --project <root> migrate --apply` (any line where `worktree-init`, `migrate` or `menu`
  follows another denied program) ran, because only the first denied program counted; it is now
  blocked with the reason of the user-run tool. Single commands and the reasons in Odoo projects
  are unchanged.
- Bash guard: an abbreviated `--project` of the entry points (`oasis --proj <dir> ...`, which
  argparse accepts) hid the command from both tiers, so `oasis --proj /p migrate --apply` ran and
  `oasis --proj /p drop-database <name>` ran without the dialog. Every unambiguous prefix of
  `--project` now takes its value like `--project`.
- `odoo-shell` refuses extra arguments with its usage (exit 2) instead of ignoring them.
- `start --detach` read only `--http-interface` itself as the address to probe: an abbreviation
  Odoo accepts (`--http-int=127.0.0.2`, `--http-i 127.0.0.2`) made it wait on the conf's address
  and stop a healthy server. Every unambiguous prefix down to `--http-i`, with `=` or a separate
  value, now counts, for the probe and the port check.
- `start --detach`: a server that did not listen in time was stopped with SIGTERM to its session
  and SIGKILL only when the server itself survived, so members of its session that ignore SIGTERM
  or outlive it were left running. After the 5 s grace every process of the server still running
  now gets SIGKILL, the server first, and processes it started meanwhile are killed too.

  service at the same moment (the second `compose up` failed with Docker's container name
  conflict): `compose up` now runs under an exclusive `flock` of a per-compose-file lock in

  checkout to start the database service.`, exit 1). Without `flock` it warns and runs
  unlocked.

  exists (created by something without a run lock); `verify-module` no longer loses a signal
  that arrives right after its locks are taken.
- `status` no longer stops before the server line and `compose ps` when `TMPDIR` is missing

  removes its locks and exits 130 or 143.

  database service and then failed with exit 1 and a generic message.

### Known limitations

- Server liveness reads `/proc`: per-checkout servers work on Linux only.
- Simultaneous `start` runs may probe and pick the same free port; start them one at a time.
- Disposable runs and `gc` read `/proc` for run-lock liveness (Linux only). SIGKILL leaves a
  disposable database behind for `gc`. A SIGTERM sent only to `verify-module` (not to its
  process group) takes effect when the phase in progress ends. A run killed after taking its
  lock but before its database existed leaves a lock that `gc` does not remove (it acts on
  existing databases); that random name stays locked. Without an absolute
  `data_dir` in `odoo.conf` filestores are not removed. With `--compact`, a SIGTERM sent only
  to the outer `test-module` process ends it without the summary; the run it started still
  finishes and drops its database.
- Only `-p`, `--http-port <port>` and `--http-port=<port>` are recognized as explicit ports;
  abbreviations such as `--http-p` reach Odoo but are not checked or recorded.

  tools to the `gentle-ai-worker` and `gentle-ai-verify` subagents; it does nothing when the
  overlay is up to date (see the README, Subagents).
- Session notice: in an Odoo project, oasis reminds the user once per session to run
  `/odoo19 setup` when the overlay is missing or outdated.

### Changed

- Per-checkout database names: in a checkout with a slug (a linked worktree, or any checkout
  with `[tooling].checkout_slug`) the slug goes right after the managed prefix in every
  default: `install-module` uses `<dev_prefix><slug>_<module>`, `test-module` and
  `verify-module` use `<test_prefix><slug>_<module>` and its `_update` sibling, and a
  configured `test_database` becomes `<test_prefix><slug>_<rest>` (still at most 56 bytes).
  Database arguments must use that checkout namespace. The main checkout keeps its names.
- `install-module` (with or without `--with-demo`), `update-module`, `odoo-shell` and `start`
  with `-d`/`--database` now require a managed `<dev_prefix>`/`<test_prefix>` database name;
  every database name is limited to 63 bytes, and a `verify-module` test database with an
  `_update` sibling to 56 bytes.
- `update-module` and `odoo-shell` no longer create a missing database: they exit 2 with
  `Database <name> does not exist; create it with install-module or create-database.`
- The six `odoo19_*` tools are only active in Odoo projects: they are registered inactive and
  activated at session start when `.odoo19-agent.toml` is found at or above the working
  directory, so other projects pay no tokens for them. `/odoo19` stays available everywhere.

### Fixed

- `test-module --compact` in a linked worktree whose `dev/logs` links to the main checkout:
  `tools/config.py` also emits `CHECKOUT_MAIN_ROOT`, and compact runs in a linked worktree
  accept a log directory inside the main checkout's `dev/logs/odoo19`. Every other location outside the project
  is still refused.
- Browser evidence (`chrome_logs`, screenshots, videos) of `test-module` in a linked worktree
  whose `dev/logs` links to the main checkout is now copied there instead of being refused:
  `tools/common.sh` exports `CHECKOUT_KIND` and `CHECKOUT_MAIN_ROOT` to the evidence helper.

### Known limitations

- A linked worktree needs a link to the main checkout's environment file at the profile's
  `env_file` path, created by the user (agents may not create or read environment files);
  `worktree-init` is planned for 0.3.0.
- `start` without `-d`/`--database` uses the `db_name` and `--db-filter` of the project's
  `odoo.conf`; keep `db_name` out of a linked worktree's `odoo.conf`.
- Slugs are matched as prefixes: a slug that is the start of another (`wt`, `wt_1`) can reach
  the other checkout's databases.
- Checkout detection needs git 2.31 or newer; without it a worktree is treated as outside
  git and keeps the main checkout's names.
- Linked worktrees still share the HTTP port and the Compose stack (planned for 0.3.0).

## [0.1.0] - 2026-11-16

First tagged release: one project checkout per Odoo project.

### Added

- Agent-agnostic core: the `odoo19` entry point, guarded `tools/`, the six `odoo19-*` skills,
  project wrapper templates and docs.
- `install.sh` installs the committed HEAD into `~/.agents/skills/odoo19`, keeps the previous
  install as a backup and records the installed commit and version in `.oasis-install.json`.
- `odoo19 model-info <model>`: static summary of an Odoo model (definition, extensions,
  fields, overrides, methods) from the Odoo source and the project addons, without starting
  Odoo or touching a database.
- Gentle Shell layer (Pi package): project detection with a compact prompt section, the tools
  `odoo19_test_module`, `odoo19_module_status`, `odoo19_check_environment`,
  `odoo19_lint_module`, `odoo19_find_module` and `odoo19_model_info`, and the `/odoo19`
  status command.
- `odoo19_test_module` returns the result line, stats, failures with traceback tails and
  grouped warnings instead of the full log; full logs stay under `dev/logs/odoo19`.
- In Odoo projects the layer blocks agent bash commands that run `odoo-bin`, `dropdb` or
  `psql` directly and points to the guarded commands.

### Known limitations

- One checkout per project: linked git worktrees share the test database, HTTP port and
  Compose stack of the main checkout. Do not run them at the same time.
- `update-module`, `odoo-shell`, `install-module` without demo and `start -d` accept database
  names outside the managed prefixes.
- The bash guard is a guard rail, not a sandbox: piping into a shell, scripts and `ssh` are
  not detected.
