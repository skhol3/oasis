# Project capability contract (Odoo 19)

Read the current project's instructions before using this optional example. Project permissions, database guards, and validation requirements prevail. The example is a non-runtime illustration, not a machine-validated authorization schema or an installed wrapper. An existing complete `AGENTS.md` and documented guarded command interface need no template. Local wrappers are optional when an installed global entrypoint is explicitly authorized.

## One runtime source, distinct roles

For runtime paths and namespace guards, the installed tools consume the workspace file's `[tooling]` only: `community`, optional `enterprise`, `environment`, `config`, `env_file`, `compose`, `requirements`, `addons_paths`, `db_service`, `dev_prefix`, and `test_prefix`. Optional `test_database` selects a reusable sequential test target for `test-module` and `verify-module`; explicit arguments override it. It must be a nonempty suffix under `test_prefix`, use only letters/digits/underscores, and fit in 56 bytes so the separate `_update` target fits PostgreSQL's identifier limit. Without it and without an explicit argument, every `test-module` run and the tests phase of `verify-module` use a new disposable database `<test_prefix>[<slug>_]<module>_r<6 hex>` (shortened with a hash of the module to fit 56 bytes; `verify-module` adds its `_update` sibling), locked by a run lock `runs/<database>.json` in the checkout's runtime state directory, created for the run and always dropped with its filestore (`<data_dir>/filestore/<database>`, the only other `odoo.conf` option read) at the end, also after failing tests, SIGINT or SIGTERM; names ending in `_r<6 hex>` (optionally `_update`) are reserved for them. `gc` lists the disposable databases of the checkout's namespace without a live run lock and `gc --apply` drops them (`--all-checkouts` widens the listing to every slug; dropping other namespaces is refused in a checkout with a slug); development databases and test databases without the run suffix are never touched. This setting does not authorize a reset or concurrent use; see [test destinations](../../docs/testing.md#reusable-test-destinations-and-compact-evidence). Optional `checkout_slug` names this checkout's identity: the reader reports `CHECKOUT_KIND` (`main`, `linked` or `none` outside git) and `CHECKOUT_SLUG` from a read-only `git rev-parse` (when git fails, a project with no `.git` at or above its root is `none`, a `.git` file — a linked worktree — fails closed unless `checkout_slug` is set, and a `.git` directory fails closed); a linked worktree derives the slug from its directory name, a `checkout_slug` set in the checkout's `oasis-checkout.toml` (1-20 of `a-z`, `0-9`, `_`, starting with a letter or digit) always wins, and an underivable name requires it. With a slug, every default database name gets `<slug>_` right after its managed prefix (`<dev_prefix><slug>_<module>`, `<test_prefix><slug>_<module>_r<6 hex>`, a configured `test_database` becomes `<test_prefix><slug>_<rest>` and must still fit in 56 bytes), and every database argument must start with `<dev_prefix><slug>_` or `<test_prefix><slug>_`; without a slug the previous names and the managed-prefix rule hold. All database commands, including `update-module`, `odoo-shell`, `install-module` and `start -d`, require a managed name of at most 63 bytes; `update-module` and `odoo-shell` refuse a missing database instead of creating it. See [checkout identity](../../docs/checkouts-and-worktrees.md#checkout-identity) and [databases per checkout](../../docs/checkouts-and-worktrees.md#databases-per-checkout). The reader also reports `CHECKOUT_MAIN_ROOT` (the main checkout's work tree for `linked`, the project root for `main`, empty outside git and for a linked worktree whose git failed but whose `checkout_slug` is set). Preparing a linked worktree: it needs nothing but `git worktree add`, below the workspace file or anywhere else (it then reads its main checkout's workspace file through git); `worktree-init <feature> <branch> [--path <dir>]` (or `/oasis worktree` in Gentle Shell; Tier B in the [agent contract](../../docs/agent-contract.md): the agent proposes it and the user confirms it, then it runs with `--confirm <worktree path>`; its `--dry-run` is Tier A) creates it next to the main checkout or at the absolute `--path` (refused inside the Odoo source or another checkout, in a non-empty directory, or below another workspace file). In a linked worktree every command that starts Odoo reads only the `addons_path` of a shared `odoo.conf` and passes it as `--addons-path` with the main checkout's root replaced by the worktree's root; the main checkout's command line is unchanged. A linked worktree's `dev/logs` may link to the main checkout's: `--compact` runs accept a log directory inside `CHECKOUT_MAIN_ROOT/dev/logs/odoo19` only in a linked worktree. Optional `logs` (a path resolved from the workspace file's directory, like the other tooling paths; the reader reports it as `LOGS_DIR`, empty when absent) moves compact runs and browser evidence to `<logs>/<slug, or main for the main checkout>/run-*` (runs before 0.8.0 used `<logs>/odoo19/<slug or main>/`; they are left where they are), refused with `Compact logs must remain inside the configured logs directory.` when that directory resolves outside `<logs>`; without it they stay under `dev/logs/odoo19`. See [preparing a linked worktree](../../docs/checkouts-and-worktrees.md#preparing-a-linked-worktree). Optional `data_dir` (a path resolved like the other tooling paths; reported as `DATA_DIR`, empty when absent) is passed to every Odoo launch as `--data-dir=<path>`, and disposable runs and `gc --apply` then remove filestores under it instead of the `odoo.conf` `data_dir`; an `odoo.conf` without `addons_path` makes every Odoo launch, in the main checkout and linked worktrees alike, get `--addons-path=<enterprise>,<each addons_paths root>,<community>/addons` (an `odoo.conf` with `addons_path` keeps the rules above), so the `odoo.conf` can be free of location-dependent paths. See [path-free odoo.conf](../../docs/path-free-odoo-conf.md). Optional `lint_rcfile` is consumed only by `lint-module`; existing commands ignore it. `model-info` reads only `community`, optional `enterprise` and `addons_paths`, parses source with `ast` and needs no environment, service or database. Paths resolve from the workspace file's directory, `addons_paths` from each checkout. The source must be Odoo 19, Python the declared one (3.12 by default on 19.0), and paired `<namespace>_dev_`/`<namespace>_test_` prefixes are required; Community-only projects may omit Enterprise. `[tooling].addons_paths` alone defines operable module roots. It is guard input, never access consent, an installed wrapper, or a substitute for runtime evidence.

Workspace file: a checkout reads the nearest `oasis-workspace.toml` at or above it (searched like git searches `.git`); a linked worktree with none at or above it reads the one its main checkout reads, found through git (`git rev-parse --git-common-dir`), trusted the same way, with its slug still from its own directory name. Without either every command stops with `Missing tooling configuration: no oasis-workspace.toml at or above <checkout>.` It sets top-level `workspace_version = 1` and `odoo_version = "19.0"` (other values are refused) and the `[tooling]` keys and guards above; `version` and `python_version` derive from `odoo_version` (the series' `python_default`, 3.12 on 19.0, or a named environment's `python`) and are refused when set; its paths resolve from the workspace file's directory, except `addons_paths`, which resolves from each checkout. `checkout_slug` is refused there: an optional `oasis-checkout.toml` in the checkout may set only `[tooling].checkout_slug` and `[tooling].environment`, the name of one of the workspace's optional `[environments.<name>]` tables (`path`, with the `[tooling].environment` rules, and `python`, within the Odoo series' range, 3.10 to 3.14 for 19.0), used instead of `[tooling].environment`; without a name a checkout uses `default`. The reader appends `WORKSPACE_ROOT` (the workspace directory), then `ODOO_VERSION`, `ODOO_SECOND_PORT_OPTION`, `ODOO_DEMO_OFF_ARGS`, `ENVIRONMENT_NAME`, `PYTHON_VERSION`, `DATA_DIR` and `AGENT_DESTRUCTIVE`; tools render version-specific Odoo options only from these (table in `tools/odoo_versions.py`). `init-dev-database` reads `[development]` and `lint-module` reads `lint_rcfile` from the workspace file. A workspace or checkout file is used only when it and its directory are owned by the current user or root and are not group- or other-writable. A checkout that still has the per-checkout file of earlier versions is refused before anything runs (exit 2, naming `oasis migrate`); converting it is `oasis migrate --apply --confirm <workspace file>`, Tier B (the agent proposes it and the user confirms it; its plan is Tier A), see [migrating to the workspace file](../../docs/migrating.md). `check-environment` and `bootstrap` check `lock.sha256` from its own directory first, then, for a legacy lock, from the project root. See the [workspace file](../../docs/workspace-file.md) and its [example](../assets/oasis-workspace.example.toml).

Servers and ports per checkout: `start` runs at most one Odoo server per checkout and records its pid and HTTP port outside the repository (`${XDG_RUNTIME_DIR:-/tmp}/oasis-<uid>/<hash of the checkout path>/server.json`, 0700). The main checkout uses the `http_port` of `odoo.conf` (8069 when absent) and refuses a busy one; a linked worktree takes the next free port after it and a free `--gevent-port`; an explicit `-p`/`--http-port` wins. Only `http_port`, `gevent_port` and `http_interface` are read from `odoo.conf` for this. `stop` stops only this checkout's server; `stop --database` stops the shared database service only when no other checkout has a live server, and never stops another checkout's Odoo. `status` and `/oasis` report this checkout's server. Test runs (`test-module`, the tests phase of `verify-module`) and `start --stop-after-init` always get their own free `--http-port` and a distinct free second port (`--gevent-port` on 19.0) unless one is given. See [servers and ports per checkout](../../docs/servers-and-ports.md).

Environment contract: `doctor` checks the configuration, git 2.31+, docker and `docker compose version`, flock, `/proc`, the environment's Python, the Odoo release, odoo.conf, the compose file's top-level `name:`, the env file (exists, account variables not empty), the logs and data directories, the HTTP port and that Odoo's database account logs in (`postgres_connection`; a refused account names the Tier B `recreate-database-volume --confirm <compose project>` when the volume was initialized with other credentials), read-only (no service started, no file contents or values printed), and ends with `doctor_failures=<n>` (exit 1 when `n > 0`); `check-environment` then checks the locks. See [checking the environment](../../docs/checking-environment.md).

Optional `[odoo].addons_paths` describes consultation roots, not operable modules. Optional `[environment].dependency_inputs`, `lock_files`, and `lock_fingerprint` describe dependency evidence. Optional `[commands]` describes existing command discovery, not dispatch or permission: either existing project-relative wrapper paths (`check_environment`, `bootstrap`, `install`, `update`, `test`, `module_status`) or an explicit installed `entrypoint` such as `~/.agents/skills/odoo19/oasis` (or its compatibility alias `~/.agents/skills/odoo19/odoo19`, identical in behaviour; likewise `/odoo19` and the inactive `odoo19_*` Gentle Shell tools alias `/oasis` and the `oasis_*` tools) with known operation names such as `check-environment`, `install-module`, and `odoo-shell`. The direct form may declare `odoo_shell`. Expand `~` only for a reviewed user executable path; pass `--project` and the absolute project root as separate arguments, never as shell text. Do not invent flags, fallback scripts, or commands. File paths resolve relative to the config directory; legacy wrappers remain project-relative.

The workspace file may also declare `[odoo].version` and `community`, `[environment].python` and `config`, and `[database].test_prefix`. These are *optional advisory duplicates*, not additional runtime authority: the installed reader accepts them only when they agree with `[tooling]` and rejects conflicts. A new workspace file need not declare them. No custom interpolation or relabeling of the runtime fields is required.

The optional `[development]` section is consumed only by the explicit `init-dev-database [--with-demo] <module> <database>` command, not by test, install, update or server commands. It declares `administrator_login` and optional `[[development.users]]` entries with `login`, `name` and nonempty `groups` (installed `res.groups` XML IDs); it never contains passwords or overrides `[tooling]` paths or namespaces. Optional `demo_modules` is a unique list of technical module names installed, in order, only with explicit `--with-demo`, before the selected module. The default remains no demo and does not install those optional modules. This uses Odoo's native manifest demo loader and never changes addon dependencies or automatically edits project configuration. Initialization requires an explicitly approved fresh development database; it needs no terminal: passwords are generated into `<database>.logins` next to the env file (mode 0600, never printed), and on a terminal a person may type their own with the echo off. Existing databases are refused, never reset. See the [account setup guide](../../docs/dev-database.md).

## Optional standalone module lint

Declare `[tooling].lint_rcfile` as a nonempty path to an existing trusted Pylint configuration, resolved from the workspace file's directory; an external path still requires exact access consent. The configured isolated Python must provide Pylint and pylint-odoo supporting the declared Odoo target. Run the full installed entry point with `--project /absolute/project lint-module <module>`. The whole module must be under a configured addon root inside this project. Pylint rules/plugins stay in the rcfile; CLI targets override its Odoo/Python version settings and disable persistence/bytecode writes. Missing config/tools fail clearly; there is no dependency installation, Odoo runtime/config read, database/service operation or automatic fix. Trusted plugins/hooks are executable code, not sandboxed. Existing commands and `verify-module` do not gain a lint phase. See the [lint guidance](../../odoo19-testing/references/pylint-odoo-guidance.md).

## Boundaries before operations

Before external workspace path access, obtain exact per-target human consent; declarations never supply it. Never search arbitrary external roots or print/log secret-bearing runtime config contents; no oasis workflow requires reading, copying or typing a password (the generated env file is the database account of the service and of Odoo, see [The database account](../../docs/setup.md#the-database-account)). Confirm matching Odoo 19 `release.py` and permitted Python runtime evidence before lifecycle operations; missing evidence is not confirmation. Use only a project-isolated environment. Preview environment creation or sync and obtain authorization for the exact target; never mutate global packages or shared virtualenvs. Even quick diagnostics may trigger shimmed environment installation, so assess safety first. If an authorized source or guarded command is unavailable, report it rather than improvising.

Never connect agents to production. Require explicit approved local database names, not guessed defaults. A declared prefix alone is not reset permission: destructive reset additionally requires an exact named disposable test database, explicit authorization, a guarded installed interface enforcing the namespace, and active-session checks. Never auto-stop or terminate sessions; only a run's own disposable databases and `gc --apply` (Tier A in the [agent contract](../../docs/agent-contract.md): the agent runs it) close sessions and drop databases; `drop-database` and `gc --apply --trash` are Tier B there: the agent proposes them, the user confirms them, and they run with `--confirm <database>` and `--confirm <project root>`; a refusal names the exact command. `oasis policy --json` lists every tier. Do not bypass guards with raw SQL. Fresh installation, tests, current-code update and historical migration remain distinct evidence; report skipped checks.
