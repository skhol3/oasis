# Project capability contract (Odoo 19)

Read the current project's instructions before using this optional example. Project permissions, database guards, and validation requirements prevail. The example is a non-runtime illustration, not a machine-validated authorization schema or an installed wrapper. An existing complete `AGENTS.md` and documented guarded command interface need no template. Local wrappers are optional when an installed global entrypoint is explicitly authorized.

## One runtime source, distinct roles

For runtime paths and namespace guards, the installed tools consume `[tooling]` only: `version`, `python_version`, `community`, optional `enterprise`, `environment`, `config`, `env_file`, `compose`, `requirements`, `addons_paths`, `db_service`, `dev_prefix`, and `test_prefix`. Optional `test_database` selects a reusable sequential test target for `test-module` and `verify-module`; explicit arguments override it. It must be a nonempty suffix under `test_prefix`, use only letters/digits/underscores, and fit in 56 bytes so the separate `_update` target fits PostgreSQL's identifier limit. Without it and without an explicit argument, every `test-module` run and the tests phase of `verify-module` use a new disposable database `<test_prefix>[<slug>_]<module>_r<6 hex>` (shortened with a hash of the module to fit 56 bytes; `verify-module` adds its `_update` sibling), locked by a run lock `runs/<database>.json` in the checkout's runtime state directory, created for the run and always dropped with its filestore (`<data_dir>/filestore/<database>`, the only other `odoo.conf` option read) at the end, also after failing tests, SIGINT or SIGTERM; names ending in `_r<6 hex>` (optionally `_update`) are reserved for them. `gc` lists the disposable databases of the checkout's namespace without a live run lock and `gc --apply` drops them (`--all-checkouts` widens the listing to every slug; dropping other namespaces is refused in a checkout with a slug); development databases and test databases without the run suffix are never touched. This setting does not authorize a reset or concurrent use; see [test destinations](../../README.md#reusable-test-destinations-and-compact-evidence). Optional `checkout_slug` names this checkout's identity: the reader reports `CHECKOUT_KIND` (`main`, `linked` or `none` outside git) and `CHECKOUT_SLUG` from a read-only `git rev-parse` (when git fails, a project with no `.git` at or above its root is `none`, a `.git` file — a linked worktree — fails closed unless `checkout_slug` is set, and a `.git` directory fails closed); a linked worktree derives the slug from its directory name, a set `checkout_slug` (1-20 of `a-z`, `0-9`, `_`, starting with a letter or digit) always wins, and an underivable name requires it. With a slug, every default database name gets `<slug>_` right after its managed prefix (`<dev_prefix><slug>_<module>`, `<test_prefix><slug>_<module>_r<6 hex>`, a configured `test_database` becomes `<test_prefix><slug>_<rest>` and must still fit in 56 bytes), and every database argument must start with `<dev_prefix><slug>_` or `<test_prefix><slug>_`; without a slug the previous names and the managed-prefix rule hold. All database commands, including `update-module`, `odoo-shell`, `install-module` and `start -d`, require a managed name of at most 63 bytes; `update-module` and `odoo-shell` refuse a missing database instead of creating it. See [checkout identity](../../README.md#checkout-identity) and [databases per checkout](../../README.md#databases-per-checkout). The reader also reports `CHECKOUT_MAIN_ROOT` (the main checkout's work tree for `linked`, the project root for `main`, empty outside git and for a linked worktree whose git failed but whose `checkout_slug` is set). Preparing a linked worktree: it needs its own profile, a `dev/odoo.conf` with its own `addons_path`, and a link to the main checkout's environment file at the profile's `env_file` path; agents may not create or read environment files, so the user runs `worktree-init <feature> <branch>` (or `/odoo19 worktree` in Gentle Shell), which creates the worktree next to the main checkout and prepares all three, and agents are blocked from running it. When `config`, `env_file`, `compose` and `requirements` all resolve outside the checkouts (a shared configuration directory), `worktree-init` copies only the profile, and in a linked worktree every command that starts Odoo reads only the `addons_path` of the shared `odoo.conf` and passes it as `--addons-path` with the main checkout's root replaced by the worktree's root; the main checkout's command line is unchanged. Its `dev/logs` may stay linked to the main checkout: `--compact` runs accept a log directory inside `CHECKOUT_MAIN_ROOT/dev/logs/odoo19` only in a linked worktree. Optional `logs` (a path resolved from the checkout, like the other tooling paths; the reader reports it as `LOGS_DIR`, empty when absent) moves compact runs and browser evidence to `<logs>/odoo19/<slug, or main for the main checkout>/run-*`, refused with `Compact logs must remain inside the configured logs directory.` when that directory resolves outside `<logs>`; without it they stay under `dev/logs/odoo19`. See [preparing a linked worktree](../../README.md#preparing-a-linked-worktree). Optional `lint_rcfile` is consumed only by `lint-module`; existing commands ignore it. `model-info` reads only `community`, optional `enterprise` and `addons_paths`, parses source with `ast` and needs no environment, service or database. Paths resolve from the explicit project root. The source must be Odoo 19, Python must be 3.12, and paired `<namespace>_dev_`/`<namespace>_test_` prefixes are required; Community-only projects may omit Enterprise. `[tooling].addons_paths` alone defines operable module roots. It is guard input, never access consent, an installed wrapper, or a substitute for runtime evidence.

Servers and ports per checkout: `start` runs at most one Odoo server per checkout and records its pid and HTTP port outside the repository (`${XDG_RUNTIME_DIR:-/tmp}/oasis-<uid>/<hash of the checkout path>/server.json`, 0700). The main checkout uses the `http_port` of `odoo.conf` (8069 when absent) and refuses a busy one; a linked worktree takes the next free port after it and a free `--gevent-port`; an explicit `-p`/`--http-port` wins. Only `http_port`, `gevent_port` and `http_interface` are read from `odoo.conf` for this. `stop` stops only this checkout's server; `stop --database` stops the shared database service only when no other checkout has a live server, and never stops another checkout's Odoo. `status` and `/odoo19` report this checkout's server. Test runs (`test-module`, the tests phase of `verify-module`) always get their own free `--http-port`. See [servers and ports per checkout](../../README.md#servers-and-ports-per-checkout).

Optional `[odoo].addons_paths` describes consultation roots, not operable modules. Optional `[environment].dependency_inputs`, `lock_files`, and `lock_fingerprint` describe dependency evidence. Optional `[commands]` describes existing command discovery, not dispatch or permission: either existing project-relative wrapper paths (`check_environment`, `bootstrap`, `install`, `update`, `test`, `module_status`) or an explicit installed `entrypoint` such as `~/.agents/skills/odoo19/odoo19` with known operation names such as `check-environment`, `install-module`, and `odoo-shell`. The direct form may declare `odoo_shell`. Expand `~` only for a reviewed user executable path; pass `--project` and the absolute project root as separate arguments, never as shell text. Do not invent flags, fallback scripts, or commands. File paths resolve relative to the config directory; legacy wrappers remain project-relative.

Legacy profiles can still declare `[odoo].version` and `community`, `[environment].python` and `config`, and `[database].test_prefix`. These are *optional advisory duplicates*, not additional runtime authority: the installed reader accepts them only when they agree with `[tooling]` and rejects conflicts. A canonical new profile need not declare them. No custom interpolation or relabeling of the runtime fields is required.

The optional `[development]` section is consumed only by the explicit `init-dev-database [--with-demo] <module> <database>` command, not by test, install, update or server commands. It declares `administrator_login` and optional `[[development.users]]` entries with `login`, `name` and nonempty `groups` (installed `res.groups` XML IDs); it never contains passwords or overrides `[tooling]` paths or namespaces. Optional `demo_modules` is a unique list of technical module names installed, in order, only with explicit `--with-demo`, before the selected module. The default remains no demo and does not install those optional modules. This uses Odoo's native manifest demo loader and never changes addon dependencies or automatically edits project configuration. Initialization requires an explicitly approved fresh development database and hidden terminal password entry. Existing databases are refused, never reset. See the [account setup guide](../../README.md#fresh-development-database-with-role-accounts).

## Optional standalone module lint

Declare `[tooling].lint_rcfile` as a nonempty path to an existing trusted Pylint configuration, resolved from the explicit project root; an external path still requires exact access consent. The configured isolated Python must provide Pylint and pylint-odoo supporting the declared Odoo target. Run the full installed entry point with `--project /absolute/project lint-module <module>`. The whole module must be under a configured addon root inside this project. Pylint rules/plugins stay in the rcfile; CLI targets override its Odoo/Python version settings and disable persistence/bytecode writes. Missing config/tools fail clearly; there is no dependency installation, Odoo runtime/config read, database/service operation or automatic fix. Trusted plugins/hooks are executable code, not sandboxed. Existing commands and `verify-module` do not gain a lint phase. See the [lint guidance](../../odoo19-testing/references/pylint-odoo-guidance.md).

## Boundaries before operations

Before external workspace path access, obtain exact per-target human consent; declarations never supply it. Never search arbitrary external roots or read/log secret-bearing runtime config contents. Confirm matching Odoo 19 `release.py` and permitted Python runtime evidence before lifecycle operations; missing evidence is not confirmation. Use only a project-isolated environment. Preview environment creation or sync and obtain authorization for the exact target; never mutate global packages or shared virtualenvs. Even quick diagnostics may trigger shimmed environment installation, so assess safety first. If an authorized source or guarded command is unavailable, report it rather than improvising.

Never connect agents to production. Require explicit approved local database names, not guessed defaults. A declared prefix alone is not reset permission: destructive reset additionally requires an exact named disposable test database, explicit authorization, a guarded installed interface enforcing the namespace, and active-session checks. Never auto-stop or terminate sessions; only a run's own disposable databases and a user-run `gc --apply` close sessions and drop databases. Do not bypass guards with raw SQL. Fresh installation, tests, current-code update and historical migration remain distinct evidence; report skipped checks.
