# Project capability contract (Odoo 19)

Read the current project's instructions before using this optional example. Project permissions, database guards, and validation requirements prevail. The example is a non-runtime illustration, not a machine-validated authorization schema or an installed wrapper. An existing complete `AGENTS.md` and documented guarded command interface need no template. Local wrappers are optional when an installed global entrypoint is explicitly authorized.

## One runtime source, distinct roles

For runtime paths and namespace guards, the installed tools consume `[tooling]` only: `version`, `python_version`, `community`, optional `enterprise`, `environment`, `config`, `env_file`, `compose`, `requirements`, `addons_paths`, `db_service`, `dev_prefix`, and `test_prefix`. Optional `test_database` selects a reusable sequential test target for `test-module` and `verify-module`; explicit arguments override it. It must be a nonempty suffix under `test_prefix`, use only letters/digits/underscores, and fit in 56 bytes so the separate `_update` target fits PostgreSQL's identifier limit. Absent configuration preserves legacy module-derived defaults. This setting does not authorize a reset or concurrent use; see [test destinations](../../README.md#reusable-test-destinations-and-compact-evidence). Optional `lint_rcfile` is consumed only by `lint-module`; existing commands ignore it. Paths resolve from the explicit project root. The source must be Odoo 19, Python must be 3.12, and paired `<namespace>_dev_`/`<namespace>_test_` prefixes are required; Community-only projects may omit Enterprise. `[tooling].addons_paths` alone defines operable module roots. It is guard input, never access consent, an installed wrapper, or a substitute for runtime evidence.

Optional `[odoo].addons_paths` describes consultation roots, not operable modules. Optional `[environment].dependency_inputs`, `lock_files`, and `lock_fingerprint` describe dependency evidence. Optional `[commands]` describes existing command discovery, not dispatch or permission: either existing project-relative wrapper paths (`check_environment`, `bootstrap`, `install`, `update`, `test`, `module_status`) or an explicit installed `entrypoint` such as `~/.agents/skills/odoo19/odoo19` with known operation names such as `check-environment`, `install-module`, and `odoo-shell`. The direct form may declare `odoo_shell`. Expand `~` only for a reviewed user executable path; pass `--project` and the absolute project root as separate arguments, never as shell text. Do not invent flags, fallback scripts, or commands. File paths resolve relative to the config directory; legacy wrappers remain project-relative.

Legacy profiles can still declare `[odoo].version` and `community`, `[environment].python` and `config`, and `[database].test_prefix`. These are *optional advisory duplicates*, not additional runtime authority: the installed reader accepts them only when they agree with `[tooling]` and rejects conflicts. A canonical new profile need not declare them. No custom interpolation or relabeling of the runtime fields is required.

The optional `[development]` section is consumed only by the explicit `init-dev-database [--with-demo] <module> <database>` command, not by test, install, update or server commands. It declares `administrator_login` and optional `[[development.users]]` entries with `login`, `name` and nonempty `groups` (installed `res.groups` XML IDs); it never contains passwords or overrides `[tooling]` paths or namespaces. Optional `demo_modules` is a unique list of technical module names installed, in order, only with explicit `--with-demo`, before the selected module. The default remains no demo and does not install those optional modules. This uses Odoo's native manifest demo loader and never changes addon dependencies or automatically edits project configuration. Initialization requires an explicitly approved fresh development database and hidden terminal password entry. Existing databases are refused, never reset. See the [account setup guide](../../README.md#fresh-development-database-with-role-accounts).

## Optional standalone module lint

Declare `[tooling].lint_rcfile` as a nonempty path to an existing trusted Pylint configuration, resolved from the explicit project root; an external path still requires exact access consent. The configured isolated Python must provide Pylint and pylint-odoo supporting the declared Odoo target. Run the full installed entry point with `--project /absolute/project lint-module <module>`. The whole module must be under a configured addon root inside this project. Pylint rules/plugins stay in the rcfile; CLI targets override its Odoo/Python version settings and disable persistence/bytecode writes. Missing config/tools fail clearly; there is no dependency installation, Odoo runtime/config read, database/service operation or automatic fix. Trusted plugins/hooks are executable code, not sandboxed. Existing commands and `verify-module` do not gain a lint phase. See the [lint guidance](../../odoo19-testing/references/pylint-odoo-guidance.md).

## Boundaries before operations

Before external workspace path access, obtain exact per-target human consent; declarations never supply it. Never search arbitrary external roots or read/log secret-bearing runtime config contents. Confirm matching Odoo 19 `release.py` and permitted Python runtime evidence before lifecycle operations; missing evidence is not confirmation. Use only a project-isolated environment. Preview environment creation or sync and obtain authorization for the exact target; never mutate global packages or shared virtualenvs. Even quick diagnostics may trigger shimmed environment installation, so assess safety first. If an authorized source or guarded command is unavailable, report it rather than improvising.

Never connect agents to production. Require explicit approved local database names, not guessed defaults. A declared prefix alone is not reset permission: destructive reset additionally requires an exact named disposable test database, explicit authorization, a guarded installed interface enforcing the namespace, and active-session checks. Never auto-stop or terminate sessions. Do not bypass guards with raw SQL. Fresh installation, tests, current-code update and historical migration remain distinct evidence; report skipped checks.
