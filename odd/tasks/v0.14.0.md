# v0.14.0 (plan): `oasis setup` and a layout-free configuration

Approved by the user (L4). Goal: a new project goes from
twelve manual steps (docs/new-workspace.md) to cloning the repository and running one command,
without tying the user to a directory layout.

## Specs

- S1. User, reading docs/new-workspace.md: "veo que el usuario debe hacer como mil cosas ajaja -
  como reducimos esa cantidad? que podriamos "automatizar?"; then "investiga formas mas sencillas,
  talvez gentle-shell haga algo similar u otras herramientas"; on the proposal: "si me parece
  mejor". One command, `oasis setup`, user-run (agents never run it: it writes configuration):
  - prints the plan and changes nothing by default; `--apply` writes (like `gentle-shell setup
    --dry-run` and `oasis migrate --plan`);
  - conventions before questions: infers project, checkout and Odoo series from where it runs
    and from what exists; the series' Python and PostgreSQL come from tools/odoo_versions.py; it
    asks only what it cannot infer (for example where the Odoo source is, Enterprise or not);
  - adopts what exists and never overwrites (like `gentle-shell home import-pi`): existing
    odoo.conf, compose file, environment, locks and databases are used; only missing pieces are
    created;
  - creates what is missing: the workspace file, a path-free odoo.conf, a compose file with
    PostgreSQL, requirement inputs, locks and the uv environment;
  - `doctor` names the command that fixes each FAIL.
  Target flow: clone the repository; `oasis setup` (plan); `oasis setup --apply`; `oasis doctor`.
- S2. User: "mis dudas ahora son respecto a los directorios para el source, el repo y los
  worktrees, como se manejara? ademas la idea es no atar una estructura de directorios".
  Configuration in three levels, each value in one place:
  - machine, `~/.config/oasis/config.toml`: the source path of each series (community,
    enterprise) and where environments go by default; written once by `oasis setup`, detected or
    asked; checked like the workspace file today (owner, not group/other writable);
  - project, `oasis-workspace.toml`: database prefixes, compose, logs, odoo.conf; it no longer
    has to repeat the source paths;
  - checkout, `oasis-checkout.toml` (optional): worktree slug, chosen environment.
  `doctor` shows where each value came from.
- S3. User: "al hacerlo asi cualquier proyecto con odoo 19 apunta al source donde se le de la gana
  verdad?" Yes: the machine file gives the default per series; a project overrides any value in
  its workspace file, and the project value wins.
- S4. Worktrees anywhere (no layout tie): today the workspace file must sit at or above every
  checkout (tools/config.py:188 find_workspace walks up like git). New: when no workspace file is
  found above a linked worktree, oasis asks git for the main checkout (`git rev-parse
  --git-common-dir`) and uses the main checkout's workspace file; the slug still comes from the
  worktree directory name. `worktree-init` keeps creating `<main>-<slug>` next to the main
  checkout by default and accepts `--path`. The upward search stays, so existing layouts work.
- S5. The Python environment without a required directory name: today it must be inside the
  checkout or under a directory whose name ends in `environments`. New: any directory that is an
  environment (has pyvenv.cfg) or does not exist yet, keeping the two guards: it is not and does
  not contain the Odoo source, and it does not contain a checkout.
- S6. `oasis setup` proposes a layout when there is none (the corpus-cafe one as the example) and
  accepts any other; with an existing layout it only fills the gaps.

- S11. User: "en mi repo de corpus cafe tengo ramas, entre ellas note que hay diferentes versiones
  para odoo 15 ... como haria la configuracion para odoo15? ya que oasis esta quitando ataduras a
  directorios como lo gestionamos ahora?"; on the proposal: "si dale". In this version only the
  guard: when the checkout's module manifests carry a series-style version (`<series>.x.y.z`)
  for a series other than the configured `odoo_version`, oasis refuses before running anything
  (exit 2, naming the module, both series and how to fix it), and doctor reports it as one FAIL.
  Manifests without a series-style version are ignored. This matters because S4 lets a worktree
  of another branch (e.g. origin/15.0 in corpus-cafe) read the main checkout's 19.0 workspace.

## Not in this version

- Isolation controls between projects (user: "por el momento no"): unique database prefixes per
  shared PostgreSQL server, sharing environments only between identical locks, pinning the
  expected source commit in doctor. Recorded in memory oasis/backlog.
- `oasis source <series>` to clone the Odoo source.
- Odoo 15.0 support (next version): the series per checkout (`odoo_version` in

  series, the decision recorded in memory oasis/backlog 2b).
- oasis_* tools reaching other worktrees (memory oasis/new-worktree-not-registered).

## Decisions (user, 2026-11-24)

- S7. Project environment file: `setup` writes only the variable names with empty values (user:
  "Solo los nombres, vacíos"); it never generates or prints a password, never overwrites an
  existing file, and creates it 0600. `doctor` reports empty required values as FAIL with what
  to fill in (names only, never values).
- S10. Machine file (user: "vamos que la B, arranca", choosing B among: A project only, B machine
  file, C environment variables, D cascading files, E automatic search): the machine file is
  optional; without it everything works as today (each project declares its source). With it,
  its values are defaults the project overrides. `setup` may suggest a source path it finds, never
  choose it silently. User, asked what "optional" meant: "por defecto que sea el de maquina": the
  machine file is the default place for the source paths: `setup` writes them there (creating the
  file), new workspace files do not repeat them, and docs present the machine file as the normal
  way; a project declares a source only to override it. Existing workspace files that declare it
  keep working.
- S8. `--project` optional (user: "Sí"): without it, the checkout is the git top level of the
  current directory (or the current directory outside git); `--project` keeps working as today.
- S9. Locks (user: "setup y bootstrap --apply"): both `setup --apply` and `bootstrap --apply`
  compile the locks from the requirement inputs when they are missing or stale, then sync.
