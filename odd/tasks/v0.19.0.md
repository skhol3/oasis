# oasis v0.19.0: a recipe per series, from one source

The code skills keep one recipe per task, now written for each supported series: on a 15.0 checkout the
agent follows the 15.0 recipe, on 19.0 the 19.0 one. One source per recipe renders every series.

## Specs

- S1. Recipes per series (user: "la idea es para un contruir un model si estamos en la version 15
  seguimos tal receta, si estamos en la 19 su receta correspondiente, y asi con todo lo demas"). The
  four code skills (`odoo-backend`, `odoo-views-frontend`, `odoo-security`, `odoo-testing`) hold
  `references/<series>/<recipe>.md` for every series `tools/odoo_versions.py` supports, with the twelve
  recipes of v0.18.0 (module, model, compute-constraint, inheritance, access, record-rules, views,
  actions-menus, view-inheritance, owl-component, model-tests, tours). Each one's example works as
  written on its series. Each example is self-contained: it uses only what its own recipe and
  `module.md` define, so an agent building one piece in its own module copies it without reading the
  other recipes. Files several recipes show are the same copy (the v0.18.0 shared-copy test).
- S2. One source, rendered (user: "con lo planteado como podemos reducir el costo?"; approved plan:
  "Plan e implementación hasta el release"). Each recipe has one source file. Text without a marker is
  shared; a fenced block marked `since=<series>` applies from that series until a later `since` block
  of the same file replaces it. `tools/render_recipes.py` writes the per-series files, which are
  committed (install.sh installs the committed HEAD). A test renders into a temporary directory and
  fails when the result differs from the committed files. Each rendered recipe ends with a short
  section naming what differs from the previous supported series, derived from the `since` blocks, so
  no Changed in table is maintained by hand. Adding a series means adding only the blocks where it
  differs. Every rendered file keeps `Checked against:` (its series) and `Official docs:` (its series'
  page), and the v0.18.0 checks (sections, parsable blocks, shared copies, official page per series)
  run on every rendered series.
- S3. Rules in Odoo's format (research of the official Odoo skills, `odoo/odoo` 20.0 `skills/`): each
  recipe's usual mistakes are rules with `Why`, `Exceptions` and a bad and a good code block. The text
  is ours: nothing is copied from Odoo (S8).
- S4. Series-free skills: no SKILL.md names a series in its description or body; the body says to run
  `oasis doctor` and open `references/<series>/` for its `series=` (else `odoo_release=`), and the
  series-specific rules now in the bodies move into the recipes. Every test reads the series from
  `tools/odoo_versions.py`; none hardcodes `15.0` or `19.0`. `odoo-environment` and
  `odoo-module-lifecycle` keep their `references/<series>.md`, read through the same list.
- S5. Index in the project context (research: "In 56% of eval cases, the skill was never invoked",
  vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals). The Gentle Shell project context
  names the project's series and the recipe directories for it, in a few lines, so an agent sees the
  route without opening a skill first. A contract change (mirrored prompt): its own commit and a
  README note.
- S6. Verification by script (user: "explicame el dos, como que ya habia un script?"): a tool builds the
  recipes' module of a series into a directory, ready for `oasis test-module --compact library`; the
  suite checks without a database that the built module is complete (every manifest file has a source)
  and parses. The release gate's step 7 uses it on every supported series.
- S7. Evals per series (research: Anthropic "Build evaluations first"): `docs/recipe-evals.md` lists,
  per series, tasks where another series' forms are wrong (for example `<tree>` or `attrs` on 19.0,
  `models.Constraint` on 15.0), and a script checks a module for the forbidden forms of its series. The
  release gate runs them with an agent on each series and the row records the result.
- S8. License (choice: "Apache-2.0, sin copiar texto de Odoo"): the repository gets the Apache-2.0
  `LICENSE` its skills already declare; from Odoo only the structure and links are taken, never text.
- S9. Release gate (AGENTS.md Releases step 0): the field run on openalliance-odoo (15.0) and
  corpus-cafe (19.0); the release is blocked if handoffs grow over 0.18.0 (1, genuine).

## Not in this version

- Odoo 20.0 and pointing to the `skills/` Odoo ships in its source from 20.0 (they exist only on 20.0
  and master).
- A loop where an agent proposes recipe fixes by itself from a failed check (detection by S6 and S7 is
  in; the fix stays a reviewed change).
- test-module reporting skipped tests; `setup --plan --json` asking the series in JSON; existing
  workspaces' dev.in.
