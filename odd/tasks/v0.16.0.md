# oasis v0.16.0: agent-first consolidation

The agent contract, generated credentials and conversational setup live in the core CLI, for any
agent; the harness layer (pi/) only adds UX. Sources: Engram #5830 (field run on
openalliance-odoo, 11 issues) and #5831 (decisions). One version in chained PRs (P1..P5).

## Specs

- S1. Agent contract in the core (#5831 decision 1): ONE policy table (operation, tier, reason) in
  the core, source for docs, skills, menu, messages and any harness guard. Changing a tier is a
  contract change (decision + README + CHANGELOG, AGENTS.md Compatibility).
  - Tier A (agent does it alone; reversible/rebuildable): setup --apply, bootstrap,
    create-database, start/stop, install/update, doctor, gc --apply, tests. Agent-usable entry
    points where missing.
  - Tier B (agent proposes, human confirms; data loss or hard to undo): worktree-init
    ("con diálogo"; --dry-run free), migrate --apply, drop-database, gc --apply --trash, a NEW
    oasis operation to recreate the database volume (replaces raw `docker compose down -v`),
    creating a new branch. User: "--confirm + diálogo del harness si hay": the CLI requires
    `--confirm <exact name>` (explicit intent, documented as such, not a guarantee against an
    agent); where a harness exists its dialog is required; agent_destructive applies to
    worktree-init "igual que drop-database".
  - Tier C (human only): typing a password, only if they want their own.
  - Error messages and doctor fix: lines name the oasis action (command, confirmation needed),
    never "ask the user" or a harness.
  - The three skills that call gc --apply user-only follow the table
    (odoo19-environment/references/project-contract.md:29, odoo19-testing/references/test-targets.md:3,
    odoo19-module-lifecycle/SKILL.md:19).
- S2. Credentials generated by oasis (#5831 decision 2, user: "oasis las genera"): setup
  generates the PostgreSQL user and password in ONE 0600 file; Odoo and the container read that
  same source (no copy in odoo.conf, which stays path-free and password-free); no command takes a
  password as an argument or prints one (output, logs, errors); the connection check uses Odoo's
  own credentials over TCP; a volume initialized with other credentials is detected and the Tier B
  recreate is offered; the dev-db admin password is generated too (0600), typed only if the user
  wants. Guarantee: no oasis workflow requires reading, copying or typing a password. Drop the
  unenforced "agents may not read env files" claim. Existing projects (user: "Los respeta y
  ofrece migrar"): their env file and odoo.conf keep working; doctor reports; setup proposes the
  move to the single file using the current credentials, without losing the database.
- S3. Conversational configuration (#5831 decision 3): `setup --plan --json` (inferred values with
  their origin, what will be created, open questions with options and the recommended one);
  answers via flags or an answers file; no TTY requirement anywhere (setup, init-dev-database);
  known problems anticipated in the plan, not at apply: python-ldap 3.4.0 vs OpenLDAP >= 2.6
  (propose 3.4.4, #5830 item 5), uv 0.13 V7-tar sdists such as PyPDF2 1.26.0 (#5830 item 4:
  UV_LEGACY_TAR_BACKEND=1 or the remedy instead of "Fix runtime.in or its access to the package
  index"), module external_dependencies missing or conflicting with Odoo pins (#5830 item 6, e.g.
  cryptography>=3.3.1 vs 2.6.1); `oasis status --json`: what is ready, what is missing, the next
  command. The human CLI keeps working for manual use and CI.
- S4. Field-run issues (#5830):
  - 3: dependency_audit crashes on Python < 3.10 (importlib.metadata.packages_distributions).
  - 7: credentials drift between the env file, odoo.conf and the initialized volume (covered by S2).
  - 8: test-module says "not reported" for a module without tests: say "no tests ran".
  - 9: worktree-init names `git worktree prune` when a prunable entry holds the target branch.
  - 10: `/oasis setup` (Gentle Shell) only installs the subagent overlay: rename or realign, and
    say what it did.
  - 11: the default workspace inside the clone ("por que create dentro del repo lol"): prefer or
    offer the parent folder under a projects/<name>/code layout; a path to move a workspace
    created in the clone.
  - Also from this session: setup proposes series_exceptions and a checkout_slug (slug over 20
    characters) in any checkout; the slug error names the limit.
- S5. Consolidation, no new features (#5831 decision 4): reduce overlapping commands where
  possible (check-environment vs doctor, setup vs bootstrap, migrate). Panel (user: "Congelarlo
  como está"): no new panel features; it stays as is.
- S6. Release gate (user: "Sí, y bloquea la release si empeora"): before each release, a fixed
  field run from a fresh clone ("configure, test db, run tests"; "create a worktree, run tests
  there"), counting human handoffs; target 0 except genuine decisions; the release is blocked if
  the count grows over the previous release. Documented in AGENTS.md Releases. Baseline from the
  openalliance-odoo run: about 7 handoffs, 2 genuine.

## Not in this version

- New features beyond S1-S6; skills per series; oasis_* tools reaching other worktrees.
