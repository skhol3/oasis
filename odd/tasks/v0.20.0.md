# oasis v0.20.0: setup asks, and databases are the user's decision

Fixes from the v0.17.0 field run on openalliance-odoo (Engram #5839, topic
oasis/field-run-openalliance-odoo-19): setup asks for the environment and its Python, the
environment's Python is checked against the code, and creating a database needs the user.

## Specs

- S1. Environment and Python are open questions (field run, issue 1: "setup should raise environment
  location and Python as open questions (like community/enterprise) so an agent relays them, instead of
  deciding implicitly"). `setup --plan --json` lists where the environment goes (create one, and where;
  or adopt an existing one) and its Python as open questions with a recommended answer, the same way
  it asks community and enterprise, until answered. v0.15.0 S8 promised it; the field run saw zero
  questions with and without a terminal: reproduce first.
- S2. A new environment is named after the project (field run: "the proposed new env was named
  `environments/corpus-cafe-15.0` — derived from the ADOPTED env name of [tooling] (corpus-cafe, another
  project's venv) instead of the project name").
- S3. The environment's Python can load the code (field run, issue 10: billing-o15, Python 3.8, adopted
  for a 15.0 checkout whose code uses `match`; "setup (or doctor) should check the checkout's code
  parses with that Python and say so plainly (\"needs Python ≥3.10\")"). When setup adopts or creates an
  environment, and in doctor, oasis parses the checkout's Python files for that Python version and
  reports the first file that does not parse and the lowest Python the code needs.
- S4. `bootstrap --apply` exit (field run, issue 10: "bootstrap --apply exits 1 when its trailing
  doctor fails (e.g. PG not yet running) even though the sync itself succeeded — confusing"): the exit
  code reports the sync; the trailing doctor's failures are printed as such. A contract change: README
  and CHANGELOG say so.
- S5. Creating a database needs the user (field run, issues 2-3; user: «yo debo decirle crea una base,
  que pregunte asignarle el prefijo y subfijo tanto para _dev_ y _test_ claro si quiero dev o test o los
  dos»; choice: "Tier B: confirmación en consola (Recomendado)"). Every oasis command that creates a
  database is Tier B in `oasis policy --json`: a dry run shows the database it would create and the
  command waits for `--confirm <database>`; the bash guard and the Gentle Shell tools follow the policy.
  Disposable test databases of `test-module` stay as they are. Scope (L5): `create-database` and
  `init-dev-database` always; `install-module` only when the database does not exist (choice: "Pasa a
  Tier B solo cuando crearía"); the kept test database of `test-module`/`verify-module` (`--reuse`,
  `[tooling].test_database`) stays Tier A (choice: "No, es parte de testear (Recomendado)").
- S6. The database's name and kind are asked (same quote): before creating, the plan asks the name
  parts around `_dev_` and `_test_` (prefix and suffix), whether dev, test or both, the module and
  whether with demo data (demo only when asked: «salio con ya creo y valio»). An agent relays the
  questions; nothing is chosen for the user.
- S7. Administrator password (field run, issue 4: «El admin su contraseña hay que dejarle la default»;
  answer now: "si para cualquier base, pero si debe permitir poner otra si se pide igual mediante el
  .env"): a database oasis creates keeps Odoo's default administrator password for every database; when
  the project's env file sets an administrator password variable, oasis uses it instead. Extra users
  only when declared in `[development]` / `[[development.users]]`.
- S8. No `.logins` file (field run, issue 5: the user wants the generated `<database>.logins` file
  gone, «apesta»): oasis writes no password file; what a login uses is said in the output (the default
  or "from <env file> <variable>"), never a secret value.
- S9. Compose and `.env` (field run, issue 6, a question): docs say that docker compose reads the `.env`
  of its own directory for interpolation and why oasis still passes `--env-file` (the env file can be
  configured elsewhere). No behavior change.
- S11. Real run of the daily commands on both series (user: "me refiero a oasis, mas que todo me refiero
  a comandos para levntar, testaer, y demas herramientas ... se cubrio para las dos versiones que estamos
  manejando hoy?"; proposal accepted: "si"). The release gate gains a step that runs, against a real
  Odoo and PostgreSQL of each supported series: `init-dev-database` without and with demo (through the
  S5 confirmation), `start --dev` with the series' dev features and a stop, `restart`, `update-module` on
  the dev database and `odoo-shell` (one command in, its output out), recording per series each command's
  exit and what it proved. The suite gets a 15.0 test for `odoo-shell` (today none) and any command the run
  shows untested on a series.
- S12. One command creates a database (L12; choices: "Sí: un creador, retirar create-database" and, for
  the questions, "Idioma, País"). `init-dev-database` is the only command that creates a database, the way
  Odoo's database manager form does: its plan asks the name (suffix), dev, test or both, the module, demo
  data, the language and the country, then the dry run and `--confirm`. `install-module` installs only into
  an existing database: on a missing one it refuses, exit 2, naming the init-dev-database plan.
  `create-database` is removed (contract change: README note with what a user or wrapper runs instead); the
  menu, the project wrapper, status `next` and the docs follow. Disposable and kept test databases of
  test-module and verify-module are unchanged. This replaces the S5 scope line for install-module.
- S10. Release gate (AGENTS.md Releases step 0): the field run on openalliance-odoo (15.0) and
  corpus-cafe (19.0), with S1, S5 and S6 driven by an agent through the plan; handoffs: the new database
  confirmation is a genuine decision; the release is blocked if non-genuine handoffs grow over 0.19.0.
